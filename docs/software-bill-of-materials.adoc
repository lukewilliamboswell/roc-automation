= Publish and consume software bills of materials

An SBOM gives a downstream user a machine-processable inventory of the
components in a specific release, their identities and their relationships.
Generate it from the resolved build and the delivered files, and distribute it
with the release. Include first-party, open-source and proprietary components;
a private component is still a component.

The read-only build task discovers components, generates the SBOM and validates
its schema and coverage. The shared publisher transfers and verifies the
supplied files as inert bytes.
A checksum file, Blueprint lock or GitHub dependency submission alone does not
meet this contract.

[#risk-component-evidence]
== Risks and controls for component evidence

An inventory can omit transitive/native components or describe a different
binary while still passing schema validation. Bind composition claims to exact
subjects and preserve explicit uncertainty. Generate from resolved inputs and
reviewed composition metadata; independently validate graph references, subject
hashes, targets and declared coverage before publication. Test with query fixtures
that locate known transitive components and distinguish build-only from shipped
code. Agreement between producer records detects inconsistency;
it cannot prove that undiscovered components are absent or that a matched
advisory is exploitable. A supplier's document fetched beside a locked file
is bound by the file's SHA-256 and the document's own digest, and a stale
opt-out is reported rather than kept; those checks show the chain is intact,
not that the supplier's inventory is complete or authentic.

== Share generation, validation and publication responsibilities

Blueprint owns the reusable generation capability. It exposes resolved component
identities, build relationships and final artifact identities, and combines them
with reviewed repository metadata to produce the standard document. A repository
declares its deliverables and supplements missing licenses, vendored components,
native libraries and composition information. Selecting a tool in an environment
does not establish that the tool or its dependencies ship in the output.
Separate inventory inspection from final artifact binding: inspect the committed
resolved specification and lock without provisioning inputs, then hash and bind
the delivered files in the release task after the build. Missing metadata is an
explicit gap rather than a reason for an inspector to fetch, build or scan an
unrelated store tree.

roc-automation owns independent local validation and integration with its existing
publication actions. Keep the validator separate from the generator so the same
policy checks an SBOM supplied by Blueprint or another producer. The validator
reads data; it never evaluates a Blueprint file, imports candidate modules,
executes an artifact or regenerates an SBOM to make invalid input pass.

Use one generation task and one shared validation policy across release dry runs,
publication and downstream admission. Signing and publishing retain separate
authority from both. Vulnerability correlation is another consumer of the
inventory and belongs in scheduled or manually requested analysis.

== Declare what the inventory covers

Give each deliverable an explicit subject: release URL, filename, version,
target where applicable, and SHA-256 of its final bytes. Generate a separate
SBOM for each distinct target artifact, or describe every subject and its own
component graph in one document. A release-wide list with no mapping to the
individual files cannot answer which binary contains a component.

[cols="2,3",options="header"]
|===
| Inventory | Required scope

| Roc source bundle
| Source actually shipped, vendored code, and direct and transitive package or platform dependencies required by that source. Distinguish included code from dependencies fetched later by the compiler.

| Native executable or linker-input archive
| First-party code, included libraries and runtime code, including static linker inputs and generated or embedded code. Record externally provided runtime dependencies separately from the components contained in the file.

| Examples or documentation archive
| Code, scripts, fonts and other third-party material distributed in that archive. Record example dependencies without claiming they are part of a sibling binary.

| Build inputs and tooling
| Compiler, platform used by tooling, build tools and test dependencies with their versions and identities. Describe their build/test relationships in a separate inventory or explicit relationships; their use during a build does not establish that they ship inside its output.
|===

For example, a statically linked tool can contain code from its Roc platform and
native libraries even when a binary scanner cannot identify them. Use the
resolved build inputs to account for those components. Conversely, the compiler
used to build that tool is a build input unless compiler code is actually
included. Source inventories cannot by themselves establish the composition of
an optimized executable. The
https://www.cyclonedx.org/guides/OWASP_CycloneDX-Authoritative-Guide-to-SBOM-en.pdf[CycloneDX SBOM guide]
discusses generation at different stages of the build lifecycle.

State the generation context, targets, inspected inputs, exclusions and known
gaps inside the machine-processable record using the chosen format's fields,
annotations or properties. Include transitive components or link to their
accessible, immutable SBOMs with verified identities. Do not silently stop at
the first dependency layer. Unknown or withheld information is explicit, with
a contact for resolving gaps. An empty dependency list means verified absence,
not an unsuccessful scan.

== Choose an interoperable format

Publish JSON in SPDX or CycloneDX, using a maintained schema version supported
by the producer and intended consumers. Record the format and version in the
document and pin the generator and validator through the reviewed tooling
environment. One supported format is sufficient for an initial shared
implementation. Use a versioned format adapter so support for the other standard
can be added without inventing a repository-specific component inventory.
If generating both, derive them from the same inventory and check that subject
identities, component coverage and relationships agree.

Use a unique document identity, revision, creation/update timestamp, authoring
organization and generator name/version. These identify the SBOM separately
from the software version. Record the component producer separately from the
SBOM author when they differ. Keep the metadata and relationships in the
standard document rather than in a README table that tools cannot ingest.
The https://spdx.github.io/spdx-spec/v2.3.1/document-creation-information/[SPDX document specification]
defines its document metadata.

Each component record must let a recipient distinguish it from similarly named
projects and different builds of the same project:

* producer, canonical name and exact version or source revision;
* a stable machine identifier, using an ecosystem Package URL where applicable;
otherwise a documented source/revision identity or organization-owned identifier;
* immutable source/download location, and artifact SHA-256 when those bytes are
available, distinguishing source archive hashes from binary hashes;
* declared license expression or identified proprietary terms and their location;
mark unavailable license information explicitly; and
* explicit relationships to the subject and other components, including direct
and transitive dependencies, containment and build/test use where represented.

Use actual upstream identifiers; do not invent CPE names or ecosystem package
identifiers to obtain a vulnerability match. A patched or vendored component
retains its upstream identity and records its own revision, modifications and
content identity. Preserve separate instances when targets or patches differ.
The https://spdx.github.io/spdx-spec/v2.3.1/package-information/[SPDX package specification]
defines package versions, checksums, licenses and external identifiers.

In SPDX, connect the document to its subject with `DESCRIBES` and use the
appropriate `CONTAINS`, `DEPENDS_ON`, build or test relationships between
identified elements. In CycloneDX, give each component a unique `bom-ref` and
connect it in the dependency graph; use compositions to express incomplete
coverage. A flat component array with no subject relationships is insufficient.
See the
https://spdx.github.io/spdx-spec/v2.3/relationships-between-SPDX-elements/[SPDX relationships],
https://cyclonedx.org/use-cases/software-dependencies/[CycloneDX dependency graph]
and https://www.cyclonedx.org/use-cases/compositions-dependencies/[CycloneDX coverage guidance].

== Generate and validate during the release build

The repository's read-only build task owns generation. It combines resolved
package metadata and the final artifact inventory with reviewed supplemental
metadata for components the generator cannot discover. Supplementary metadata
belongs with the build recipe and changes through review, rather than an
untracked manual edit to a generated SBOM.

Implement the following sequence in the release task and its pull-request dry
run:

. Build and test the exact deliverables, then calculate their final hashes.
. Generate the SBOMs for those files, including the subject hashes. Keep them
as sidecar assets to avoid a self-referential archive checksum.
. Validate JSON against the pinned standard schema locally. Reject duplicate
identifiers, unresolved relationship references, missing subjects, mismatched
target identities or subject hashes, and unexplained omissions from the known
resolved component inventory. Schema validity alone does not prove completeness.
. Test useful queries: locate a known transitive dependency and its source,
trace it to each affected subject, and distinguish a build-only tool from a
shipped library. Include proprietary/vendored fixtures where applicable.
. Upload the tested artifacts and their validated SBOMs from this same run.
The publisher transfers them as inert bytes, verifies their names, sizes and
hashes after upload, and publishes them together without rebuilding.

The repository chooses a generator with demonstrated support for its actual
inputs. A tool that recognizes other package ecosystems is not evidence that
it discovers Roc imports, bundled platform/native code or vendored inputs.
Pin and cache generators like other tools. Routine validation uses local
schemas and metadata; remote vulnerability queries and full advisory rescans
belong in a separate scheduled/manual analysis job so they do not delay PR CI.

[#generate-sidecars-with-the-shared-actions]
=== Generate sidecars and chain suppliers' SBOMs with the shared actions

Blueprint ships the generation capability above as a standalone tool with
`inspect`, `bind` and `check`: a Roc app bundle,
`roc-blueprint-sbom-<hash>.tar.zst`, since 0.7.0, and a native
`blueprint-sbom-<system>` binary per system since 0.8.0, which also lists a
produced archive member by member and writes an evidence manifest beside the
sidecars. Its own releases publish `.spdx.json`, `.cdx.json`,
`.spdx-2.3.json` and the manifest beside every asset. Two shared actions wire that tool into a
repository's release build so each project does not repeat the steps:

* xref:actions.adoc#sbom-sidecars[`actions/sbom-sidecars`] runs in the
  read-only build job after the final files exist. It exports the evaluated
  Spec and the Lock, inspects the reviewed composition for one target, binds
  the sidecars to each listed file's final bytes with a creation time and
  namespace taken from the tested commit, checks them offline, and returns the
  complete asset set for the test jobs, the attestation step and
  `actions/publish-release`. The tool bundle and the Roc release it needs are
  recorded per Blueprint release in `actions/setup-blueprint/sbom-tools.json`,
  so `Blueprint.roc` remains the one place a repository names its release.
* xref:actions.adoc#fetch-dependency-sboms[`actions/fetch-dependency-sboms`]
  is the one step that uses the network. For every component the composition
  takes from a locked `SourceFile` or fetched program, it looks for the
  supplier's sidecar beside the locked URL by the naming convention, records
  the document with its SHA-256 and identity bound to the Lock's digest, and
  writes `sbom/imports.json`. `inspect` then verifies the binding and folds the
  supplier's graph into the inventory under the import's prefix, so the chain
  is transitive: package, platform, application.

The repository keeps `sbom/composition.json` under review, one per release
target where targets differ, and decides where the imports live. Committing
`sbom/imports.json` keeps the release build offline and stable and makes a
supplier's changed document a reviewed change, which is the recommended
default; a scheduled job can run the fetch action and propose the update.
Fetching in the release build itself is also supported, at the cost of a
network dependency on release day. Either way the fetch action refuses to
adopt bytes that differ from a recorded digest.

The release fails, in the pull-request dry run as well as on release day, when
a locked dependency has neither a bound supplier SBOM nor a reviewed
`unavailable_sboms` entry. The fetch action reports a stub for the maintainer
to complete with a real reason and contact; it never invents the opt-out, and
an opt-out whose supplier now publishes a sidecar is reported as stale so it
gets removed. A dependency pinned by a tree or NAR digest cannot be bound,
because that digest is not the file's SHA-256; pin the file by its published
hash to chain it, or record why it is not. Every gap appears as an
`incomplete` coverage scope in the documents and in the job summary.

The sidecar action also returns a `roc-automation-sbom-evidence-v1`
envelope, the producer's input to the independent validator and privileged
publisher handoff: each file and sidecar by name, size, SHA-256, format,
target and version, bound to the source commit and the producing run, with
the digest of the inventory each subject was bound from. A Blueprint release
whose `bind` writes an evidence manifest beside the sidecars has it checked,
listed in the asset set and recorded in the envelope, and one whose tool
lists a produced archive member by member has every member of a source
bundle accounted for before the inventory is bound. The
complete release in `examples/sbom-chain/` builds a bundle and a native
executable for each supported system in read-only jobs, tests the exact
files, attests every asset with its sidecars and publishes the explicit
asset list through `actions/publish-release`.

The version accepts SemVer prerelease identifiers, including the shared
`0.0.1-dry-run` label; numeric prerelease identifiers cannot have leading
zeroes. Build metadata (`+...`) is not supported for release identities.
For a `source` target, member enumeration applies to `.tar.zst` bundles only.
Other files, including ZIP archives and PDFs, use the reviewed composition
without tar extraction. This prevents an unrelated deliverable from being
misread as a Roc bundle; it does not discover that deliverable's contents.
Use a separate invocation and composition when its contents differ. Regression
tests bind a mixed bundle, ZIP and PDF release and verify that their inventories
remain distinct and that every sidecar stays mapped to its own subject.

The chain into a native consumer depends on Blueprint admitting a `source`
supplier into a native inventory, which Blueprint 0.8.0 does and 0.7.0
refused with `import target differs from subject`. The fetch action records
the supplier's stated target, so the bound import is accepted, and the
example's chain check requires the executable's SBOM to carry the supplier's
graph on every system.

The shared actions cover bundles and binaries first; an examples or
documentation archive is listed in `files` only when the repository has a
reviewed composition for it. A fetched supplier document's digest proves that
the bytes did not change after review, not that the supplier wrote them.
Attesting a supplier's sidecar at admission, and the independent validator and
evidence envelope the publisher hands off, remain separate work that these
actions neither replace nor weaken.

=== Validate a declared release inventory

Give the shared validator three explicit inputs: the final release files, their
declared SBOM-to-subject mapping, and the resolved component/coverage inventory
from the build. Each mapping identifies the SBOM filename, format/version and
SHA-256, plus each subject's filename, size, SHA-256 and target. Also bind the
inputs to the source repository, commit and producing workflow run/attempt.
Use a deliberate target-independent identity for source-only subjects rather
than silently substituting the validator host's target.

This mapping is a release envelope, not a second SBOM format. Component records,
dependency relationships and coverage statements remain in the standard
document. The resolved inventory is evidence to compare, not authority to invent
missing component identities or declare that environment tools are contained.
Checking one producer's records against each other detects inconsistency; it
cannot establish that the producer discovered every component.

The validator applies the following checks locally:

* Read a bounded set of regular files within the selected artifact directory;
reject symlinks, duplicate JSON keys, duplicate names and undeclared files.
* Validate against the reviewed schema and semantic rules for the declared
format/version. Bundle schemas and their references with the pinned validator;
do not fetch schemas, component URLs or external references while validating.
* Recompute every declared file hash and size, and require each SBOM subject
and target mapping to agree with the exact delivered bytes. An SBOM hash does
not substitute for its subject's hash.
* Reject duplicate element identifiers, conflicting identities and unresolved
relationship references. External document references must resolve to supplied,
hash-verified records or be recorded as an explicit coverage gap. Respect the
standard's relationship direction and distinguish containment, runtime
dependencies, build dependencies and test dependencies.
* Compare the component graph with the resolved inventory and reviewed metadata.
Reject missing required subjects, unexplained component omissions and coverage
claims stronger than the supporting evidence. Preserve legitimate distinct
instances of a component when their target, revision or patch differs.
* Report known gaps separately from successful checks. Explicit unknown metadata
is useful information; it is not evidence of complete coverage. Required scope
with unresolved gaps blocks release admission until policy accepts a reviewed,
bounded exception or the inventory is corrected.

Emit a deterministic machine-readable validation report with the validator and
policy version, schema identity, input digests, subject mappings, stable
diagnostic codes and coverage findings. A nonzero exit status prevents release
admission. Keep the report's input order and diagnostics stable, and exclude
host paths and current-time values from its identity. A report supplied by the
candidate is diagnostic evidence: the trusted admission job independently
rechecks its bindings and required local validation with pinned reviewed code.

Test malformed documents and query behavior as well as valid examples. Include
wrong-target and swapped-subject hashes, duplicate and dangling references,
unreachable transitive components, conflicting component instances, an empty
scan presented as complete, and a build-only compiler incorrectly claimed as
shipped. Verify that disconnected build-only records do not make an affected
binary appear to contain that tool, and that declared incomplete coverage never
turns an absent query result into proof of absence.

=== Reuse the existing publication paths

For ordinary product and tool releases, use `actions/publish-release` to transfer
the complete declared asset set, including the validated SBOM sidecars and
retained evidence. Its name, size and download/hash verification preserves the
exact tested bytes; that transfer check is separate from SBOM validation.
Choose the asset set explicitly so a missing required sidecar cannot be hidden
by a successful wildcard match for unrelated release files.

For linker-input releases, use `actions/publish-build-inputs` and its versioned
release manifest. Declare every SBOM sidecar and evidence file with its size,
digest and subject/target mapping. Extend the manifest schema deliberately when
adding these records; never admit arbitrary extra files or treat them as target
archives. Attestation checks, upload, download verification, draft recovery and
immutable-release verification cover the complete declared file set. The lock
retains the selected manifest identity so the mapping remains bound to the same
source and artifact identities. See
xref:linker-input-releases.adoc#trusted-publisher-contract[the linker-input publisher contract].

The attestation job checks the selected run, source and complete mapping before
signing. A build-provenance statement about an SBOM file and an SBOM statement
about a software artifact have different subjects and predicates; preserve both
identities where both are produced. Do not attribute a candidate build to the
publisher's own source revision. Publish retained bundles alongside the
inventory, and verify them during adoption rather than ordinary cache reuse.
These responsibilities extend the existing publisher and admission boundaries;
they do not require another independent SBOM publisher.

Provenance and an SBOM provide different evidence: provenance describes the
producer and build context, while an SBOM describes composition. A signed SBOM
attestation can bind the document to the exact artifact digest. Sign or attest
the SBOM using reviewed signing infrastructure, retain the signature or bundle,
and document the expected signer/workflow and verification command. A signature
establishes an authenticated statement, not the accuracy of its inventory.

Keep write authority out of generation. GitHub attestations require dedicated
attestation/OIDC permissions; if used, a separate job runs pinned reviewed code
without checking out or executing candidate sources. It signs only inert bytes
from the selected build run, bound to that run's exact source and subjects.
Do not grant these permissions to a job running PR code. See
https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations[GitHub's SBOM attestation guidance]
and xref:artifact-verification.adoc#separate-admission-from-routine-use[artifact admission].

== Distribute and retain the evidence

Publish sidecars such as `<asset-name>.spdx.json` or `<asset-name>.cdx.json`
alongside the corresponding immutable release assets. Release notes identify
the mapping, format, scope and documented gaps and link to the SBOM and its
signature/attestation evidence. Workflow artifacts with short retention are
not the downstream distribution channel.

Retain the documents and all referenced component SBOMs for supported releases.
For restricted components, provide authorized recipients access to sufficient
identity and relationship data and a documented contact; do not silently omit
them. Public metadata must exclude secrets, internal credentials and absolute
developer paths.

An SBOM correction increments its document revision and retains the original.
Publish corrections at a new immutable location, still bound to the unchanged
subject digest, and cross-link the revision history from the advisory or
documentation. Never replace a published asset or mutate an immutable release
to correct its inventory. Changed software bytes require a new software release.

== Consume and act on the inventory

At release adoption, download the SBOM for the exact selected artifact, validate
its format and subject SHA-256, verify the expected signature/attestation, and
retain the admitted record with the artifact identity. Preserve upstream
identities and relationships when incorporating components into your own SBOM;
make referenced documents available to your recipients too.

Index component identifiers, versions, revisions and hashes for supported
releases. Scheduled analysis or a new advisory can then query that inventory,
produce the affected release/target list and trace the relationship to the
component. A maintainer reviews candidate matches, local patches and actual
usage, records the decision and any fix/advisory, and publishes an updated
release when needed. An SBOM is not a vulnerability verdict: a database match
may need investigation, and no matches do not establish absence of risk.
Absence from an incomplete inventory is not evidence that a component is absent.

GitHub can
https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/establish-provenance-and-integrity/export-dependencies-as-sbom[export its repository dependency graph as SPDX].
That is useful input, but it reflects the graph GitHub knows. Establish the
exact release subject, target-specific composition and unsupported dependencies
before using it as a delivered-artifact SBOM. Dependency submission, lockfiles,
provenance attestations and hash inventories retain their separate purposes.

The
https://www.cyber.gov.au/publication/2026-minimum-elements-for-a-software-bill-of-materials-sbom[2026 joint SBOM minimum-elements guidance]
covers machine-processable formats, metadata, component identity, sharing and
updates. This chapter applies those concerns to our release process; checking
in configuration or producing a syntactically valid document does not establish
compliance with that guidance.
