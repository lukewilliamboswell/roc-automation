= Project-practice evidence

Keep evidence for the technical behavior the model aims to establish. A shared
configuration records an intended practice; the corresponding execution or
observation establishes whether it worked. Assess the shared tooling, workflow
boundaries and evidence within the scope of this manual. Product-specific
security claims and project governance remain with maintainers.

[#risk-evidence-claims]
== Risks and controls for evidence claims

A maintainer can mistake a template, green check or external score for proof
of a broader property. Match each claim to evidence of the behavior it actually
names. Keep an inventory of applicability, verification, source links and
unresolved questions; review actual execution and operational history where
required. Distinguish source-policy checks, compatibility, composition and
producer provenance. External assessment criteria can expose omitted questions,
but their applicability and any project governance obligations remain the
maintainer's responsibility.

== What the model specifies and what needs evidence

[cols="1,2,2",options="header"]
|===
| Area | Specified practice | Per-project evidence to review

| Change control
| Actions pinned by full SHA, signed commits, pull requests for every tooling change
| Public history, effective review rules, maintained releases

| Testing
| A check task on every pull request, exact-artifact release tests, a daily compatibility run
| Meaningful project tests, a documented invocation, tests for new behavior

| Analysis
| A named place for code scanning workflows
| Analysis suited to the project's own languages; findings resolved

| Dependencies
| Dependabot pull requests for actions; locked tools and bundles
| Dependency inventory, reviewed upgrades, timely vulnerability fixes

| Delivery
| Immutable releases, content hashes verified locally, provenance reviewed at adoption
| The actual release history and its notes

| Reporting
| A `SECURITY.md` and private reporting enabled
| Working report channels and the actual response history

| Documentation
| A manual rendered and deployed by a shared action
| Project purpose, interface documentation, contribution requirements, license
|===

== Keep an evidence inventory

For each project, maintain an evidence inventory. It is an internal review aid;
the public documentation should explain what readers need without discussing a
badge application.

[cols="1,3",options="header"]
|===
| Field | What to record

| Criterion or practice | A short statement of the behavior being assessed
| Applicability | Applicable, not applicable with a reason, or unresolved
| Public evidence | A stable URL to documentation, releases, repository settings, or history
| Verification | The CI check, manual review, or operational observation that tests the claim
| Status | Met, incomplete, or needs investigation; never infer this from a template
| Owner and review date | Who maintains the evidence and when it was last checked
| Follow-up | A linked issue or pull request for missing work
|===

At minimum, review this inventory:

[cols="1,3",options="header"]
|===
| Area | Evidence to locate and verify

| Project entry points | Purpose, supported scope, obtaining a release, feedback, discussion, and contribution links
| Legal | Project license in a standard location and applicable third-party notices
| Documentation | Basic use, a working first example, public inputs and outputs, commands, configuration, formats, and APIs
| Change control | Public version history, reviewable interim changes, unique release versions, immutable tags, and human-readable release notes
| Reporting | Searchable issue history, enhancement path, private vulnerability channel, and actual response history
| Build and tests | Clean source build, documented test command, CI execution, and a policy to test significant new behavior
| Analysis | Appropriate warnings, linters, static analysis, dynamic analysis, and timely treatment of findings
| Dependencies and delivery | Reviewed updates, dependency inventory, HTTPS delivery, locally verified content hashes, provenance review at adoption, and credential checks
| Maintenance | Recent activity, supported versions, vulnerability handling, and periodic review of stale claims
|===

xref:documentation.adoc#cover-the-public-project-experience[Cover the public project experience]
expands the documentation row into an authoring and review process. Verify that
the configured reporting channel works. Review repository permissions and branch
rules against actual successful checks, including signed commits where required.

== External assessments

External criteria can help maintainers find an omitted risk or organize their
own evidence. OpenSSF Best Practices covers a wider project than this manual's
technical scope; Scorecard measures another set of observable practices. Neither
configuration nor a tool score establishes an entire project's badge status.
Maintainers assess applicability and any governance requirements separately.
Revisit the underlying evidence when behavior changes, rather than treating
an old assessment as continuing proof.

For those separate assessments, consult the
https://www.bestpractices.dev/en/criteria[OpenSSF criteria] and
https://github.com/ossf/scorecard/blob/main/docs/checks.md[Scorecard check definitions].
