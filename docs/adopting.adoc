= Adopt the model in a repository

This chapter is for a maintainer bringing a repository in line with the model.
It assumes the earlier chapters. Work from a fresh branch of the remote default
branch, and open one pull request per numbered step so that a failure points at
one change.

A xref:overview.adoc#a-pure-roc-package[Roc package] follows every step,
with one runner in each workflow. The sentences below that begin "A platform"
and the acceptance item that begins "For a platform" do not apply to it.

For a Roc package using released utilities and fixed downloaded tooling, start
with xref:pure-package.adoc#adopt-a-pure-package-without-nix[Adopt a Roc package without Nix]. It includes a
complete Blueprint recipe, lock review, cache lifecycle and executable handoff.

[#risk-adoption-evidence]
== Risks and controls for adoption evidence

Copying a starter can leave stale paths, unrelated task names or missing
product cases while producing plausible configuration. Adopt through observable
behavior. Run the documented local tasks, a release dry run and the published
suite; inspect the resulting files and test the required-check and issue-reporting
failure paths. Keep configuration-specific fixes in the adopting repository and
common fixes in the shared tool. Adoption evidence establishes the exercised
integration, not every feature of the product or every future utility version.

== Steps

. *Environment.* Add `Blueprint.roc` and `Blueprint.lock` with the shared
  utilities and every tool and toolchain the repository uses. Add `roc-stable`
  and source dependencies only for tooling the repository itself runs from
  source. Using the released `blueprint` binary, confirm that its named tasks
  run the selected utilities. Remove any `flake.nix`,
  `flake.lock`, `.envrc` or other environment definition this replaces, and add
  `.blueprint/` to `.gitignore`.
. *Tasks.* Use the
  xref:shared-utilities.adoc#share-automation-through-executable-utilities[shared utility skeleton]
  for common operations. Configure Blueprint tasks rather than copying their
  implementations. Consolidate overlapping scripts and delete one that only
  repeats another test. Keep product-specific source tooling in Roc following
  xref:repository.adoc#write-automation-as-roc-scripts[Write product-specific automation as Roc scripts].
  Carry each script's tests across first, as `expect` tests or cases the check
  script runs. Delete the original only when its replacement runs in CI.
. *Pins.* Remove `.roc-version`, `.github/roc-nightly.json` and every `roc`
  header field outside `scripts/`. Set the `roc` field of every script to the
  `roc-stable` tag. Make the check script enforce both. A platform also
  commits its generated host bindings and adds the check that regenerates and
  compares them.
. *Examples.* Point every Roc application in the repository at the working tree
  by relative path. Record expected output. Remove any step that rewrites
  committed examples after a release.
. *Release artifacts.* Add tasks that build the bundle, the examples archive,
  the documentation archive and the manual, and a task that tests the archive
  against a loopback bundle. Generate and locally validate an SPDX or CycloneDX
  SBOM for each final artifact as described in
  xref:software-bill-of-materials.adoc#publish-and-consume-software-bills-of-materials[the SBOM contract],
  including transitive components and exact subject digests;
  xref:actions.adoc#sbom-sidecars[`actions/sbom-sidecars`] and
  xref:actions.adoc#fetch-dependency-sboms[`actions/fetch-dependency-sboms`]
  do this with a reviewed `sbom/composition.json`. Arrange immutable
  downstream distribution and authenticated evidence without granting write
  permissions to jobs executing repository code.
. *Workflows.* Replace the repository's workflows with `ci.yml`, `release.yml`
  and `nightly.yml`, plus any
  xref:optional-workflows.adoc#optional-workflows[optional workflows] it needs.
  Call `actions/setup-blueprint` with no inputs, after the checkout; it
  installs the release that `Blueprint.roc` names. A repository that tests on
  Windows lists `"x86_64-windows"` in its `Systems`, names roc-blueprint 0.9.0
  or later, and leaves `install-nix` unset in its Windows jobs.
. *Repository settings.* Apply
  xref:settings.adoc#repository-settings[Repository settings], update the
  required check names, and delete branches that earlier automation owned.
  Confirm the result with the `check-settings` task, as
  xref:settings.adoc#confirm-the-settings[Confirm the settings] describes.

== Acceptance

Record a link for each item in the final pull request.

* `blueprint run check` passes locally, using the released `blueprint` binary
  and a current nightly `roc` on `PATH`.
* A search finds no `.roc-version`, no `roc: "` header field outside `scripts/`, no committed flake
  files, no rendered documentation, and no Python, bash or PowerShell
  automation.
* `ci.yml` passes on the pull request, and its log shows the `blueprint`
  checksum verified before `blueprint run check`.
* A `release.yml` dry run produces every release asset, and the archived
  examples differ from the repository's only in the package dependency.
* The dry run validates each SBOM's schema, artifact/target digest and
  relationships, and a query identifies a known transitive component and its
  source. Documented coverage gaps are reviewed; the release process makes the
  documents and signature evidence available downstream.
* A manual `nightly.yml` run passes against the latest release.
* A deliberately failing nightly run opens exactly one tracking issue, a second
  failure comments on it, and a passing run closes it.
* `blueprint run check-settings -- <owner>/<name>`, run from roc-automation,
  passes every line for the repository.
* A real pull request with a failing check is blocked from merging.
* For a platform: a deliberate edit to the committed bindings fails `ci.yml`.

== Evidence for each claim

A claim about the repository is only as good as the check behind it.

[cols="2,3",options="header"]
|===
| Claim | Evidence

| CI runs the reviewed `blueprint` binary
| The setup step verifies the download's SHA-256 against the reviewed value before running it

| Tooling uses the pinned compiler
| Scripts start with the `roc-stable` shebang; CI prints `roc-stable version`

| Nothing but the scripts is pinned
| The check script fails when a `roc` header field or `.roc-version` exists outside `scripts/`

| Every script names the tooling compiler
| The check script fails unless each script's `roc` field equals the `roc-stable` tag in `Blueprint.roc`

| Repository examples test the working tree
| The check script fails unless each application names the relative package path

| Examples behave as documented
| The check script compares each example's output with the recorded specification

| A platform's bindings match the compiler
| `ci.yml` regenerates them with the latest nightly and fails on a difference

| Published examples work
| `release.yml` tests the archive before upload; `nightly.yml` tests the published archive

| Published bytes are the tested bytes
| The publish job downloads each uploaded asset and compares it with the tested artifact

| A release identifies its components
| Validated SPDX/CycloneDX documents bind the exact deliverables to their component graphs, with source identities, explicit gaps and retained downstream access; schema validity alone does not prove coverage

| The release names its compilers
| Release notes contain both version strings

| The repository settings are in place
| The `check-settings` task reads them from GitHub and passes every line

| The latest release works on the latest nightly
| The most recent `nightly.yml` run, and the absence of an open tracking issue
|===
