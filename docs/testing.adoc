= Test in pull-request CI

Code that only compiles proves little. That is true of examples, and equally of
tests, benchmarks, fuzz targets and fixtures. Anything in the repository that is
not run goes stale without anyone noticing, and is found broken on the day it is
needed.

The rule is that every Roc program in the repository runs in pull-request CI,
even if only briefly. This chapter says what runs, how much of it, and how the
tests are organised.

== What runs on every pull request

[cols="2,3",options="header"]
|===
| Check | What it runs

| Formatting
| `roc fmt --check` over the repository's Roc sources

| Unit tests
| `roc test` on the package or platform root

| Examples
| Every example, built once and run against its recorded cases

| Integration tests
| The test driver, over its full list of cases

| Benchmarks
| A smoke run: each benchmark builds and completes one small iteration

| Fuzz targets
| A smoke run: each target builds and replays its committed corpus

| Scripts
| The `expect` tests of the modules under `scripts/src/`
|===

The `check` task runs all of these, so a contributor runs the same set with
`blueprint run check` before opening a pull request.

== Heavy runs stay out of pull-request CI

A long fuzzing campaign or a full benchmark run never runs on a pull request.
They take too long, their results vary from run to run, and a pull request
should not wait on them or fail because of noise. They run on a schedule or on
request, as described in
xref:optional-workflows.adoc#fuzzing[Fuzzing] and
xref:optional-workflows.adoc#benchmarks[Benchmarks].

What pull-request CI owes them is a smoke run. A benchmark that has not been
built since the API it measures changed will not run on the night it is
scheduled. A few seconds per target on every pull request keeps each of them
building and running, so the scheduled job measures and searches instead of
discovering that it is broken.

== Build with `--opt=dev`

Build and run with `--opt=dev` unless there is a reason not to. It compiles
quickly, which is what a test run spends most of its time on, and the checks in
this chapter ask whether the program is correct, not how fast it is.

Use `--opt=speed` only where the optimised build is the thing under test: a
benchmark's measured run, a long fuzzing campaign, or a release artifact that
ships optimised. A benchmark's smoke run in pull-request CI uses `--opt=dev`
like everything else.

== Unit tests

Run `roc test` once, on the root: `package/main.roc` for a package,
`platform/main.roc` for a platform. Roc runs the `expect` tests of every module
the root imports, transitively, so there is no need to list files or to run the
command per module. A module that the root does not reach is either dead code or
missing from the package, and either is worth knowing.

A repository with several roots runs `roc test` once on each.

== Integration tests

An integration test runs a built program and looks at what it does: its output,
its exit code, the files it writes. Organise these around an external driver
and a list of cases, not as one program per test.

.One build, many cases
[mermaid]
....
flowchart LR
    S[Application source] --> B[Build once]
    C[List of cases] --> D[Test driver]
    B --> D
    D --> R1[Run: case 1]
    D --> R2[Run: case 2]
    D --> R3[Run: case n]
    R1 --> V[Compare with expected result]
    R2 --> V
    R3 --> V
....

* *Build once.* The driver builds the application a single time and runs the
  resulting executable for every case. Compiling dominates the cost of a test
  run, so this is the difference between a suite that takes seconds and one
  that takes minutes.
* *Cases are data.* Each case names its arguments, its standard input, any
  files it needs, and the expected output and exit code. Adding a case is
  adding an entry, not writing a program.
* *Cover failure as well as success.* The same executable is run on the error
  paths: bad input, missing files, invalid arguments. A case that expects a
  particular error message and a non-zero exit code is as ordinary as one that
  expects success.
* *The driver owns the environment.* Because it sits outside the program under
  test, the driver decides how cases run. It can give each case its own process
  and working directory, run cases in parallel, set up and tear down what a case
  needs, and apply a timeout. None of that leaks into the application.
* *An update mode.* The driver accepts `--update` to rewrite expected results,
  so an intended change in behavior is a reviewed diff.

The driver is a Roc script under `scripts/`, and the cases live under `tests/`.
The expected-output specification for examples, described in
xref:examples.adoc#record-expected-output[Record expected output], is one such
list of cases run by the same driver.

== Formatting

Run `roc fmt --check` in pull-request CI, over every Roc source in the
repository. It fails the pull request that introduces unformatted code, which is
the only moment at which fixing it is cheap.

Do not run it in `nightly.yml`. A new nightly can change the formatter, and a
formatting difference says nothing about whether a release still works. The
check would raise an alarm that no patch release answers. When a new formatter
does change the output, the next pull request sees it, and reformatting is a
small pull request of its own.
