[.lead]
This manual describes an opinionated approach for managing a Roc package or
platform repository: how
its tooling is pinned, what its pull-request, release and nightly workflows
prove, and what every release contains. roc-automation holds the shared actions
that implement the parts every repository needs identically.

.How to use this manual
****
New to the model:: Start with <<how-a-roc-repository-is-maintained>> for the
compilers involved, the three workflows, and what the model leaves out.
Pure Roc package:: <<a-pure-roc-package>> says which parts of the model a
package with no host code uses, and which it skips.
Package maintainer:: Read <<pin-the-tooling-environment>>,
<<lay-out-the-repository>>, <<examples-and-the-examples-archive>>,
<<test-in-pull-request-ci>> and <<the-three-workflows>> in order.
Platform maintainer:: Read the same chapters, then
<<maintain-a-platform>> for host bindings, target matrices and native build
inputs, and <<publish-linker-inputs-from-a-pull-request>>.
Routine upkeep:: <<manual-maintenance-tasks>> lists the changes that only a
maintainer makes, and how to make each one.
Adopting the model:: Follow <<adopt-the-model-in-a-repository>> and its
acceptance list.
Reviewing trust boundaries:: Read <<automation-trust-model>> and
<<verify-released-artifacts>>.
Writing a project manual:: <<write-project-documentation>> covers the
conventions this manual itself follows.
Changing roc-automation:: <<contribute-to-roc-automation>> covers the manual
and the shared actions.
****
