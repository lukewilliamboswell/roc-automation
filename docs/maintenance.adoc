= Manual maintenance tasks

The package compiler moves by itself, every day. Nothing else does. The tasks in
this chapter are the only way the repository's tooling changes, and each is a
pull request a maintainer opens and reviews.

No workflow performs them on a schedule. A pull request opened by a workflow
with the repository's `GITHUB_TOKEN` does not start CI, so an automated update
would arrive untested and wait for a maintainer anyway. More to the point, each
of these changes decides which code runs in CI, which is a decision to review
and not a chore to automate.

[cols="2,2,3",options="header"]
|===
| Task | Files changed | When

| Update the lock
| `Blueprint.lock`
| To take newer tool versions, or to make a newer nightly selectable as `roc-stable`

| Change the tooling compiler
| `Blueprint.roc`, the `roc` field of every script, sometimes `Blueprint.lock`
| When scripts need a newer compiler, or periodically to stay close to current

| Upgrade Blueprint
| `Blueprint.roc`, `Blueprint.lock`, and the reviewed setup-action revision
| For a new roc-blueprint release

| Update script dependencies
| Script headers, `RocPackages` in `Blueprint.roc`, `Blueprint.lock`
| For a new release of a platform or package the scripts use

| Regenerate host bindings
| A platform's committed bindings
| When `ci.yml` reports that the latest nightly generates different bindings
|===

[#risk-input-upgrades]
== Risks and controls for input upgrades

An upgrade can change executable code through a URL, digest, transitive input
or compiler selection without an obvious change to the product. Treat new
identities as reviewed input changes. Update the declared recipe and lock,
inspect the resolved artifacts and run the affected tasks before adopting them.
Compiler and binding updates remain explicit maintainer work. The resulting
checks establish the selected combinations. Matching an upstream revision or
passing compatibility tests does not establish that an input is unaffected by
known vulnerabilities; advisory analysis uses its own component evidence.

== Update the lock

. Run `blueprint update`, or `blueprint update <input>` to move one input and
  keep every other pin.
. Run `blueprint run check`.
. Open a pull request whose only changed file is `Blueprint.lock`.
. Merge after `ci.yml` passes.

A lock update moves the overlay revision, the package source and tool versions.
It never changes which release is `roc-stable`, because that tag is written in
`Blueprint.roc`. It does not change the `blueprint` binary or the platform URL.

Where the repository fingerprints native build inputs, a lock change can make
those inputs stale. `ci.yml` reports that, and the fix is a new linker-input
release in the same pull request; see
xref:platforms.adoc#choose-the-correct-maintainer-path[Choose the correct maintainer path].

== Change the tooling compiler

. Choose a published nightly release.
. Change the tag in the `Command("roc-stable", ...)` setting of `Blueprint.roc`.
. Change the `roc` field in every script header to the same tag. The check
  script fails until they all match.
. If the locked overlay revision predates that release, run
  `blueprint update roc` and commit `Blueprint.lock` in the same pull request.
. Fix any script the new compiler breaks in that pull request, so the tag and
  the scripts move together.
. Merge after `ci.yml` passes.

This is a maintainer's decision for each repository. Repositories need not
agree.

== Upgrade Blueprint

A release's `blueprint` binary must be used with that release's platform URL.
`actions/setup-blueprint` reads the release from that URL. Keep that selection
in one place while migrating configuration and locked inputs together:

. Choose a roc-blueprint release.
. Move the workflows' reference to `actions/setup-blueprint` to a revision that
  records that release, if the current one does not. Dependabot proposes this
  change; xref:actions.adoc#setup-blueprint[`actions/setup-blueprint`] explains
  where the checksums are reviewed.
. Change the platform URL in the `Blueprint.roc` header.
. Migrate configuration to the release's supported Spec and run `blueprint check`.
. Run a full `blueprint update` when the release changes the lock format, review
  changed identities against the previous lock and commit the regenerated lock.
. Remove generated `.blueprint/` state when the release requires it.
. Run the affected named tasks and merge after `ci.yml` passes.

Blueprint 0.7 uses Spec major 3, Lock 2 and lock report format 2. Earlier locks
are refused by commands other than the full `blueprint update`; a named update
requires a current lock. Keep the previous lock in history for comparison.
Replace `Overlay(name, ref)` declarations with `Input(name, ref)`; the
environment's `Overlays` setting still selects which inputs act as overlays.
Declare package sources explicitly and use source-qualified tool names.
For sandboxed `Build` declarations, name an executor with
`Executor("native", Nix("pkgs"))` and select it with `Execute("native")`;
`pkgs` must name the intended declared Nix package source.
Remove generated `.blueprint/` state after migration so later builds establish
a new local explanation baseline.

External tools should read `blueprint lock show --json`, validate its public
report format and use `content_identity` and namespaced provider metadata.
Do not parse the internal representation of `Blueprint.lock`. Consumers of
build reports use `build_identity`; report and package versions are separate
compatibility contracts. Run cold and warm provisioning checks and exercise
corrupt-cache recovery: a successful lock conversion alone does not demonstrate
that the selected programs execute correctly.

No workflow file names the Blueprint version or a checksum.

Contributors then download the binary from the same release.

== Update script dependencies

. Change the release URL in each script header that uses the dependency.
. Change the same URL under `RocPackages` in `Blueprint.roc`, and add any new
  dependencies of that dependency. `roc-stable deps scripts/check_all.roc`
  lists them.
. Run `blueprint update` and commit `Blueprint.lock`.
. Merge after `ci.yml` passes.

== Maintain released utility downloads

For pure packages, `Programs` and `Fetch` lock released utilities and fixed
tooling without Nix. Change the utility recipe in `Blueprint.roc`, run
`blueprint update`, review per-system URLs, hashes, lengths and download hosts,
and commit the lock. Keep the package compiler floating independently. Native
platforms can retain Nix sources and sandboxed builds for their toolchains.

The shared artifact cache key changes with the lock and installer/registry
identity. Separate logical tool subsets use separate `cache-workload` values,
so an immutable compiler-only cache cannot claim the docs cache key. Restored
artifacts are rehashed before use and extracted trees/task links are rebuilt;
cache hits do not authenticate executables. Routine use needs no remote
attestation service. Review provenance when adopting a release, following
xref:artifact-verification.adoc#verify-released-artifacts[released artifact verification].

See xref:pure-package.adoc#adopt-a-pure-package-without-nix[the complete adoption guide] for the tested cold/warm
workflow and persistent executable handoff. The shared setup's `install-nix`
option defaults to false; opt in where the selected tools/builds need Nix.
