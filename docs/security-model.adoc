= Automation trust model

This chapter states who may do what in the workflows and shared actions this
manual describes, and why each boundary is drawn where it is. It is normative
for the shared actions in roc-automation: a change to their behavior or
permissions must keep these boundaries and arrive with regression tests for
them.

Two rules carry most of the weight:

* A job that runs repository or candidate code has no write access.
* A job with write access runs only reviewed code at a full commit SHA, and
  handles candidate output as inert files.

Read-only permissions limit repository authority; they are not a process sandbox
or proof that build outputs are benign. Code in a job can read its workspace,
use its network access and influence its outputs. Run floating compilers and
consumer code on disposable hosted runners without sensitive workload data or
publication credentials. Clearing child token variables reduces exposure but
does not isolate same-job processes from one another. Reviewed inputs, exact
source/artifact binding and consumer-facing tests remain separate controls.

Documentation source conversion, renderer builds and renderer execution also
belong in jobs with read-only tokens. The documentation and tools workflows
build the native renderer from pinned compiler and package versions. Their cache
key includes the target, compiler identity, renderer source and embedded fonts;
restored binaries still run the renderer acceptance tests. The deploy job only
receives the resulting Pages artifact. It does not compile the renderer, execute
documentation sources or restore a candidate-produced executable cache.

Optional release Pages restoration selects an explicit manual ID from the
reviewed topology after publication succeeds. The read-only `lifecycle-pages`
utility binds the strict admission report to the dispatch repository, source
and run, checks the original documentation ZIP's admitted size and digest, and
uses the shared bounded archive verifier. It accepts only the declared sole
site root with a nonempty regular `index.html`, then hands that unchanged site
to the separate Pages deployment job. It evaluates no consumer Blueprint and
runs no renderer or archived executable. This prevents an unrelated report,
wrong manual or unsafe ZIP from replacing the intended site; it does not make
archived HTML trustworthy. Publication success, the pinned controller and the
Pages environment remain workflow assumptions. Regression tests reject wrong
bindings, unsafe archives and missing roots, preserve an existing output on
failure, and compare restored files with the actual prepared ZIP byte for byte.

[#risk-execution-authority]
== Risks and controls for execution authority

A compiler, example or prerequisite script can be malicious or compromised,
and generated output can try to cross into a job that can publish or edit
issues. Separate execution from authority. Use read-only disposable test jobs,
reviewed pinned controllers in write jobs, inert data handoffs and validation
of source/run/artifact identities before writes. Security regressions exercise
wrong identities and rejected transitions. This reduces the authority available
to executed code; it does not isolate same-job processes or prove a trusted
upstream compiler produced a harmless artifact.

[#the-three-workflows]
== Shared lifecycle and separate nightly authority

[cols="2,2,3",options="header"]
|===
| Workflow and job | Token access | Runs candidate code

| Shared lifecycle Plan
| `contents: read`, `actions: read`
| No: pinned utility reads bounded immutable source/topology and GitHub metadata

| Lifecycle Validate, Host, Source, Prepare, SBOM, Seal and Candidate
| `contents: read`, with `actions: read` for exact artifact observation/transport
| Yes: source, compiler, native tasks, examples and repository Blueprint remain read-only

| Lifecycle Admit
| `contents: read`, `actions: read`
| No: pinned independent controller observes jobs/artifacts and handles bounded inert files

| Lifecycle Publish
| `contents: write`, `actions: read`, `attestations: write`, `id-token: write`, protected environment
| No: independent re-admission, exact-subject attestation/verification and inert publisher

| Optional site restore/deploy
| Restore reads inert admitted files; deploy alone has `pages: write`, `id-token: write`
| No candidate source execution or rebuild

| `nightly.yml` test
| `contents: read`
| Yes: published examples and optional default-branch native prerequisites

| `nightly.yml` selection and aggregation
| `contents: read`
| No: pinned shared runner and inert release/result metadata

| `nightly.yml` report
| `issues: write`
| No: pinned `actions/nightly-report`
|===

The shared lifecycle owns source checks and full release rehearsal, with a thin
full-SHA consumer caller. The caller's permission ceiling must permit publication,
but each executing candidate job has only read authority and no OIDC. The
always-running verdict rejects failed, cancelled or missing selected jobs and
accepts skipped stages only when planning made them inapplicable.

Only manual dispatch on the actual default branch may publish, using the event
commit and retained artifacts from its own run. The protected publisher checks
out no candidate source, evaluates no candidate Blueprint, restores no candidate
executable/package cache and executes none of the release files. Candidate data
cannot select a controller, workflow, helper or privilege level.

The nightly compatibility workflow has no contents, pull-request, actions or
status write access in any job. It cannot commit, merge, dispatch or publish.
Its report job runs `actions/nightly-report` at a full commit SHA and checks out
nothing. It receives only the outcome of the examples step, the nightly tag and
the release tag from the test job, never text produced by the examples under
test. It edits a single tracking issue, identified by its exact title and a bot
author. Every workflow in a repository shares the GitHub Actions bot identity,
so that test excludes issues opened by people and does not prove which workflow
opened the issue.

No workflow in the model opens a pull request, approves one, or merges one.
Every change to the repository is a maintainer's pull request under the
repository's own rules.

[#what-the-jobs-with-write-access-run]
=== What the jobs with write access run

The publication and nightly report jobs hold the tokens that can change a
repository's releases and issues. They run only pinned shared controllers from
the action's own copy of roc-automation. Publication first invokes independent
admission and exact-subject provenance verification, then `actions/publish-release`;
reporting invokes `actions/nightly-report`. Their trusted runtime consists of:

* Nix, installed by an install action that the shared action references by
  full commit SHA; that action fixes the Nix version and downloads its
  installer from the Nix project over HTTPS;
* the `blueprint` binary, for the release that roc-automation's own
  `Blueprint.roc` names, admitted by its reviewed SHA-256 as
  xref:security-model.adoc#the-blueprint-binary[The `blueprint` binary]
  describes;
* the environment that roc-automation's `Blueprint.lock` pins: `roc-stable`,
  which runs the script, the `gh` CLI, which makes every request, and coreutils,
  which provides `sha256sum`, plus the reviewed Python archive helper and pinned
  `zstd` used for inert archive/member verification;
* the content-addressed basic-cli platform and its dependencies, named by the
  reviewed script headers and `RocPackages` URLs; and
* the script and its modules under `scripts/` in roc-automation.

The one full SHA in the workflow's `uses:` line fixes all of these. The install
action's SHA, the recorded hashes of the binary, the lock and the script are all
files of that commit. The lock pins provider inputs by revision and content
digest; the task-only Roc bundles are pinned by their URL content hashes. Nix
takes the compiler by the hash its pinned overlay records, and takes the tools
from nixpkgs at the pinned revision, as built by its binary cache, whose
signatures it checks. Blueprint prepares missing task bundles through Roc's
verified unbundling path, described below.

Neither job checks out the calling repository, and neither action runs any of
its code. The calling repository's `Blueprint.roc`, lock and scripts play no
part. The report action reads no file from the job's workspace. The admission
controller reads bounded candidate records and files, verifies them
against independent observations and hashes the exact subjects. The publisher
reads the resulting notes and explicit public asset set, sends notes as text,
and hashes, uploads and compares assets as bytes. Neither executes them.

The token is in the environment of the one step that runs the script, where
`gh` reads it. It is never a command-line argument and is never printed, and
the scripts check every input before the first request.

Nix does not hold the token. The install action would otherwise write the job's
default token into Nix's configuration, for Nix to present to GitHub on its own
fetches. These privileged controller actions clear that setting and stop before installing
anything further if Nix still reports a token. Every input Nix fetches is public
and pinned by the lock, so it needs none.

== Compilers

`Blueprint.roc` names the release tag used for repository tooling, and
`Blueprint.lock` pins the overlay by revision and content digest. Changing the
tooling compiler is therefore a reviewed source change. Nix verifies the
compiler archive against the hash the pinned overlay revision records for that
tag. This is content integrity under a reviewed hash, as in
xref:security-model.adoc#released-artifact-verification[Released artifact verification];
it is not provenance for the upstream compiler build.

Task and shell bundles listed under `RocPackages` are not provider inputs in
`Blueprint.lock`. Their committed URLs name the content hash of each bundle.
Blueprint downloads a missing archive and invokes `roc unbundle`, which rejects
bytes that do not match that hash, before publishing the extracted package into
Roc's package cache. A bundle a script names but the environment does not list
is fetched and checked by Roc itself. Sandboxed builds cannot download: their
`RocPackages` sources are provider-locked and materialized into a separate build
package cache.

The
https://github.com/lukewilliamboswell/roc-blueprint/blob/0.8.0/docs/configuration.adoc#roc-packages[Blueprint 0.8 Roc package contract]
distinguishes Roc's extracted package cache from Blueprint's verified artifact
store. Blueprint reuses a package directory that already has
`main.roc` without rehashing that directory. Reuse therefore assumes its contents
have not been modified since verified extraction; the content-addressed URL
does not attest to an existing extracted tree. The shared privileged actions
restore no candidate-produced package cache, run no candidate code and rely on
the disposable runner's intact local cache. This does not establish integrity
of arbitrary pre-existing package caches on a maintainer's machine.

The package compiler is the latest published nightly and is not pinned. It is
installed by the official `roc-lang/setup-roc` action, referenced by full
commit SHA, from a `roc-lang/nightlies` release over HTTPS. That action does not
check a nightly download against a digest, so the compiler's integrity rests on
GitHub's release hosting and the action's pinned revision. This is accepted
because the nightly only ever runs in jobs that hold no write access. A workflow
resolves the moving release once and passes the tag to every job. Release notes
record the version used.

[#the-blueprint-binary]
== The `blueprint` binary

`actions/setup-blueprint` downloads the prebuilt `blueprint` binary from a
roc-blueprint release. Nix installation is an explicit caller option, through
an action referenced by full commit SHA, for environments/builds that need it. It builds nothing. Before the binary runs, the action checks it against
a reviewed SHA-256 and fails on a mismatch. Routine CI verifies that reviewed
hash locally and does not call an attestation service. The hash establishes
which bytes run; it is not provenance for the roc-blueprint build.

The reviewed hashes are recorded in the action, one set for each roc-blueprint
release, and are reviewed in the pull request that adds them. A caller
references the action by full commit SHA, so the hashes it trusts are fixed by
the same reference as the code that checks them. A caller may supply a hash of
its own for its runner, which then takes the place of the recorded one.

A release's binary must be used with that release's platform URL in
`Blueprint.roc`, so the action takes the release from that URL. The file is
candidate content in a pull request, and that is safe: the version it names can
only choose among releases whose hashes are already reviewed. A version the
action does not record, with no hash from the caller, fails the step.

The action accepts only a release version, from its `version` input or from
`Blueprint.roc`, and builds the download URL itself, under the roc-blueprint
releases of this project, so neither can redirect the download. The binary is
written to a private temporary file and becomes executable and visible on `PATH`
only after its hash matches. A mismatch, a release with no reviewed hash for the
runner, or a system with no released binary fails the step and installs nothing.

Blueprint 0.8 evaluates `Blueprint.roc` with its own fixed compiler, embedded in
the admitted executable and verified against its recorded SHA-256 before
extraction into the store, or an exactly matching host compiler. No GitHub
compiler download is needed for this bootstrap. The executable digest therefore
also fixes the embedded compiler archive; it does not prove that compiler
is free of defects. This compiler remains separate from fixed repository tooling
and the floating package compiler. `Programs`/`Fetch`/`Expect` environments need
no Nix; environments selecting Nix-sourced tools and sandboxed builds do.

The default executable cache is separate from the artifact store. Its exact key
includes release, system and reviewed digest. The installer copies bounded
regular bytes into a private file, hashes that copy and exposes an executable
only on a match. Corrupt regular bytes cause a fresh verified download; symlink
and nonregular cache entries are rejected. A cache hit never replaces hash
admission. Cache visibility does not establish provenance, and no moving release
lookup is needed to reuse the pinned executable.

Optional artifact caching restores only `v1/artifacts`, never extracted trees or
temporary task links. Keys separate logical tool subsets and include the lock,
installer/registry identity, Blueprint release, system and workflow. Blueprint
checks restored artifact bytes against their content identity and locked length
before use. Corrupt artifacts and their derived trees are discarded and refetched;
a mismatching download is not usable. Derived trees are rebuilt on a fresh
runner rather than trusted from a cache. GitHub cache-hit status is not admission.
Roc's package cache is separate and is not included by this action.
On native Windows the installer rejects reparse-point cache files and directories,
opens cache files without following a reparse point, and admits the copied bytes
by the same digest before exposing `blueprint.exe`. Windows uses the runner
account's filesystem ACLs rather than Unix mode bits. Artifact caching follows
Blueprint's `XDG_CACHE_HOME`, then `LOCALAPPDATA`, then `HOME/.cache` convention.
Native Windows tests exercise the installer and a real Blueprint task;
unit tests reject wrong hashes, old releases without reviewed Windows bytes
and requests for unavailable Nix. These controls assume the disposable runner
account and its parent directories have not been compromised.

`actions/blueprint-tool` runs a repository task and therefore belongs only in
read-only build jobs. The task resolves a temporary program link before its
lifetime ends; the action reports the actual file identity and can measure calls
through an optional host-side wrapper. It does not independently authenticate a
program merely because a task printed its path. The repository's reviewed Fetch
recipe and lock, plus Blueprint's verification during provisioning, supply that
admission. Privileged controllers never evaluate candidate Blueprint files or
consume candidate executable caches.

The setup action takes no token as an input. When requested, the Nix installer
can configure Nix with the job's default token. The report/publisher actions
retain their explicit token-clearing checks described above. An optional cache
requiring `id-token: write` must remain an explicit caller choice; the artifact
cache here requires no such token permission. See
xref:pure-package.adoc#adopt-a-pure-package-without-nix[the complete Roc package adoption guide].

[#independent-lifecycle-admission]
== Independent lifecycle admission

A successful candidate job or consistent checksum list can still omit a target,
misstate its producer or describe a different source. Admission reconstructs
expected obligations from the committed `release-topology.json` fetched at the
immutable tested source. It also fetches the actual run, fully paginated jobs and
artifact records. It compares the caller's literal full-SHA reusable-workflow
reference with the run's referenced workflow records. Candidate matrices, plans,
trace fields and the publisher action's own checkout SHA cannot supply authority
for the tested product source or called workflow identity.

PR merge-source identity is checked against immutable commit parents and the
actual run head. Source-only selection additionally requires a complete diff
whose live head/base still matches that tested identity; uncertainty requires
full work. A publish-only retry changes the observation attempt, not the original
producer identity. Newly produced work invalidates the old generation, and
missing/expired or ambiguous evidence blocks publication.

Exact immutable artifact IDs and service digests select the bytes to download.
Raw ZIP verification runs before bounded safe extraction; the trusted parser's
child environment omits job credentials, OIDC request variables and Python
configuration hooks. Every public file and host intermediate is rehashed and
bound to its expected original successful job and trace. Another identical copy
in Seal cannot replace the original producer. Tested native host bytes must also
match their exact owning bundle members. Public binaries require a consuming
`test-binary` obligation for every advertised target.

Final inventories must match the independently expected version, context, bundle
URLs and complete file set. Notes bind source, package/tooling compilers and final
bundle URLs/digests. SBOM checks bind both formats, manifests, retained supplier
imports and producer source/run/subject identities to actual bytes and reviewed
compositions using the supported profile's graph and coverage invariants.
Producer evidence is a nested input to the same release-evidence contract; it is
not an authorization statement or a claim of general schema conformance.

The write job repeats admission with trusted code before attesting the full
explicit public set. It verifies each provenance subject against the expected
repository, reusable workflow revision, source commit/ref and hosted runner
policy, retaining structured receipts. Publication rehashes the admitted files
before any write and downloads every uploaded asset before making the draft
public. Unknown identities, malformed receipts and conflicting draft/tag state
stop progression. Hashes and attestations establish their respective byte and
signer bindings; they do not establish a SLSA level or trustworthy product code.

Wrong-identity, shortened-matrix, stale-attempt, role/target swap, forged inventory,
host-member and publisher failure tests exercise these boundaries. Local fixtures
and mocked API/verifier tests do not prove a hosted dispatch, real signature
verification or applied environment/settings protections; record those distinct
observations when performing authorized acceptance runs. Reviewed compiler,
native adapter and composition correctness remain explicit residual assumptions.

== SBOM sidecars and supplier documents

`actions/sbom-sidecars` and `actions/fetch-dependency-sboms` belong in jobs
with `contents: read` and nothing else. Both run repository configuration:
the first evaluates `Blueprint.roc` through `blueprint spec` and runs the
Blueprint SBOM tool over the reviewed composition and the final files; the
second reads `blueprint lock show --json`. Neither holds a token that can
write a release, an attestation or an issue, and the publisher receives their
outputs as inert files, verified by name, size and digest like any other
asset.

The sidecar action selects the tool bundle by the Blueprint release that
`Blueprint.roc` names, from a reviewed record in
`actions/setup-blueprint/sbom-tools.json` fixed by the action's full SHA.
A release that ships native tool binaries has their SHA-256 reviewed in the
same record, and the binary is admitted by that digest, as `blueprint` is.
The native tool's persistent executable cache contains only bytes keyed by
release, system and reviewed digest. Bounded regular bytes are copied privately
and rehashed before every execution; corrupt bytes trigger a fresh verified
download, while symlink and nonregular entries fail. Cache hits do not prove
provenance or admit arbitrary executables. Otherwise Roc verifies the app bundle's content hash from its URL before
running it, and the action requires the Roc release the record names. The tool makes no
request while reporting. The fetch action is the one step that reaches the
network: HTTPS only, bounded to Blueprint's 1 MiB limit, with a document's
SHA-256 recorded for review and reproduced on every later run. A changed or
vanished supplier document fails the step; nothing is adopted silently. The
regression tests exercise wrong compilers, stale sidecars, a checkout that is
not the event commit, documents about other bytes, stale opt-outs and changed
records, and CI runs both actions against a consumer fixture that pins a
roc-blueprint release file by its published SHA-256: once for its source
bundle, where the supplier's SBOM is bound in, and once for a native
executable on the runner's target, whose fetched compiler has no published
SBOM and so appears as a reviewed gap and whose SBOM carries the supplier's
bundle graph bound by digest, on x86_64 Linux, arm64 Linux and Apple
Silicon. The evidence envelope the sidecar action returns names what
the publisher should receive; it authorizes nothing, and the privileged job
rechecks every file it names.

The digest of a fetched document establishes which bytes were reviewed, not
who produced them, and `inspect` establishes that the composition is
consistent with the Lock and the imports, not that it is complete. An
attestation check of a supplier's sidecar belongs at admission, as
xref:artifact-verification.adoc#separate-admission-from-routine-use[Verify released artifacts]
describes. Lifecycle admission independently checks the release transfer binding;
it does not infer supplier authorship from a digest or a producer pass flag.

== Documentation deployment

The build job of `docs.yml` runs repository sources through
`actions/build-docs` with `contents: read`. The deploy job holds `pages: write`
and `id-token: write`, runs only for the default branch, checks out nothing, and
deploys the artifact the build job uploaded. A pull request can build the site
and cannot deploy it.

== Downstream status inventory

The README's downstream version inventory is also built in the read-only
Documentation job. `scripts/downstream_status.roc` makes only GET requests,
reads immutable default-branch workflow and composite-action source as text,
and emits JSON badge data and an escaped HTML report into the Pages artifact.
It executes no downstream code. The daily schedule uses the same separate
deployment job and permissions as other documentation builds. Publication does
not commit to this repository or update a consumer. Unknown API evidence and
incomplete trees never establish that a consumer is current.

Compatibility evidence comes only from the latest scheduled caller of the
pinned shared nightly workflow. The dashboard verifies that caller at the run's
immutable SHA, the fixed aggregate gate, complete job inventory and a 48-hour
pass freshness limit. Pin-updater success is not a compatibility verdict.

== Shared release-compatibility runner

Selection, per-target tests and aggregation have only `contents: read`.
Selection resolves a release and compiler once; every target receives those
identities and verifies the selected ZIP's asset ID, length and SHA-256. The
archive is inspected for regular file types, canonical paths, duplicates,
collisions and extraction limits before it is unpacked. The reviewed Python
standard-library helper enforces the same checks on every OS, including Windows
device names, trailing-dot aliases and case-insensitive implicit-directory
collisions. It never imports archive code.

The same helper has an explicit `--artifact` profile
for workflow transport ZIPs: it omits only the examples-specific single-root
and `spec.json` requirements. Digest, size, entry-kind, canonical-path,
case/parent collision and CRC checks remain shared, and failed extraction
removes the newly created partial tree. Artifact transport tests cover inert
trace/file uploads and malformed inventories; this establishes extraction
safety, not the authority or correctness of the files. Lifecycle admission
still binds each file to its expected producer, source and role.

For a native platform, a successful host job must not stand in for proof that
the distributed bundle contains its host. The helper's `--bundle` mode hashes
the actual regular members of the digest-verified tar.zst file. The controller
runs its own pinned `zstd`, bounds the decompressed temporary regular file to
100 MB, and rejects links, special files, extension headers, duplicate/colliding
paths and hidden trailing inventories before publishing the member JSON. It
extracts and executes nothing from the bundle. Admission compares each declared
host intermediate with its owning bundle member by path, size and SHA-256.
Tests include PAX/GNU metadata, oversized streams, decoder cleanup and a real
Roc-produced bundle. These checks establish byte membership, not that a host
or its build tools behave correctly.

Published native binaries also require an exact-target candidate test. The
controller verifies their sealed source/run inventory and pre-test hashes,
passes absolute paths and digests to the reviewed read-only adapter, and
rehashes afterward. Wrong or missing bytes stop before the callback; input or
inventory changes stop its passing trace. Source correctness has its own stage
and carries no candidate-file claim. Black-box regressions cover the actual
callback handoff, source-file substitution, missing/swapped bytes and mutation.
The adapter's product assertions remain a review assumption; a successful task
is not proof of complete behavioral coverage.

Child deadlines manage Windows Job
Objects or Unix process groups, and public environment overrides cannot replace
reserved variables under any spelling of their case. Archived code and native
prerequisite code run only in the read-only test job, with checkout credentials
disabled and compiler/example child tokens cleared. That job independently
requires schedule/manual dispatch on the actual default branch and verifies
the checkout HEAD equals the event SHA before running consumer prerequisites.
Successful diagnostics are
preserved; console workflow-command markers are escaped rather than interpreted.

Suite build arguments admit only a single `--fuzz`; the runner retains the
compiler, output path and target, and selects the LLVM speed backend needed
for that admitted fuzz mode. Cases may explicitly ignore variable stderr
statistics with an empty expected stderr field. Raw diagnostics, process status,
stdout and exit assertions, deadlines and output limits still apply, so ignored
stderr cannot convert interruption into a compatibility pass.

Output matching defaults to exact bytes. Optional SGR/CR stdout normalization
compares both sides without changing raw evidence. Crash markers are checked in
raw and normalized stdout/stderr independently of comparison modes. Expected
nonzero exits cannot hide a Roc crash; the bounded libFuzzer contract alone may
expect and actually exit 77 from an admitted `--fuzz` build. Regressions cover
colored markers, ordinary expected failures and that narrow replay exception.

Expectation changes require a separate local operation with an explicit compiler;
CI and release paths cannot invoke an update implicitly. Only the source spec
marker `release: "working-tree"` admits editing; published version markers are
refused even when downloaded locally. Every executed case
must pass build, process status, exit, crash and UTF-8 checks before a spec is
rewritten. Skips are preserved and all-skipped runs refuse edits. Unknown fields
are rejected, unchanged specs retain their exact bytes, and a stale or symlinked
spec stops the final atomic replacement. These controls prevent partial or
accidental expectation changes; maintainers still review the intended output and
control the local filesystem during the edit.

Aggregation inspects result layout presence before decoding, so malformed or
unreadable duplicate evidence cannot fall back to a passing file. File and
directory types are checked without following symlink entries; regressions include
invalid UTF-8, directories and dangling links in both layouts.
Aggregation checks every declared target's identity, counts and run attempt as
inert JSON. No single matrix output can stand in for all targets. A cancelled or
failed test job cannot produce a passing issue report even when old files exist.
Reporting holds only `issues: write`, checks out nothing, and invokes the pinned
`actions/nightly-report` using only a constrained outcome and selected tags.
It receives no archive-generated diagnostic text. A complete pass can close the
issue; known test failure can open/update it; unknown, missing, skipped or
interrupted work cannot close it. Historical override runs never modify the
latest-pair tracking issue. This runner has no pin-update, pull-request, merge,
dispatch, release or deployment permission.

== Linker-input release publisher

The pull-request linker-input publisher is a separate controller action for inert,
fully declared files produced by a caller's unprivileged build jobs. A privileged
consumer workflow invokes the controller at an exact reviewed SHA. Caller source
is never checked out, imported, sourced, or executed in its privileged job.
Publication requires manual dispatch on the caller's live default-branch
commit. The controller validates the complete regular-file set and content
identities, verifies the producer's attestations, refuses mismatched existing
tags/releases, re-downloads and hashes the complete draft asset inventory, and requires immutable-release
enforcement after publication. See
xref:linker-input-releases.adoc#trusted-publisher-contract[Trusted publisher contract]
for the caller contract.

== Released artifact verification

Consumers use reviewed content hashes as the runtime identity of released
binary inputs. Routine CI verifies downloaded and cached bytes locally before
extraction or execution. It must not depend on a remote signing, transparency,
or attestation service when a reviewed hash is available. Provenance
attestations are verified when a new release or lock is adopted, during an
explicit audit, or by a downstream verifier. See
xref:artifact-verification.adoc#separate-admission-from-routine-use[Verify released artifacts] for the complete
admission and consumption policy.
