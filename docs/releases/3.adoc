= roc-automation 3

[#blueprint-parser-adoption]
== Blueprint 0.7 and parser 3 adoption

The repository and copyable pure-package starter use Blueprint 0.7.0, with
Spec major 3 and Lock 2. Explicit package sources and `Input` declarations
replace the older configuration shape. A full update replaces earlier locks;
generated local state is removed and changed pins are reviewed. Blueprint's
configuration compiler is embedded in its admitted executable, so first use
requires no GitHub compiler bootstrap request. Fixed automation pins and the
floating package compiler retain their separate roles.

Adoption checks consume `blueprint lock show --json` format 2 instead of parsing
the internal lock representation. They select fetched programs by name and
system, verify actual executable identities and exercise cold, warm and damaged
cache paths. The starter consumes the released tools 0.2.0 renderer, providing
HTML, mirrored Markdown, `llms.txt` and PDF by default.

The renderer adopts roc-parser 3.0.0 and compiler
`nightly-2026-10-21-5349569`. Its checked listing-include boundary remains
single positive tag selection and `indent=0`; broader upstream include APIs
do not implicitly expand the supported authoring contract. Independent
publication acceptance remains required when adopting changed parser output.

== Preserve component build admission evidence

The build-input publisher accepts manifest format 2 and preserves its validated
component build records in the generated lock. Format 1 remains supported.
Exact source/run/workflow binding, attestation verification, final archive
checks and lock-only publication remain required. Providers and candidate
snapshots never execute in the privileged controller.

This version applies what the first repository to adopt the model found. It
removes repeated values from every workflow, adds two shared actions for steps
that each repository had written differently, and says what the model asks of
the simplest kind of repository.

== A concrete shared utility starter

The shared utility guide gives a working Blueprint consumer, a producer layout
and interface conventions for new tools. The existing pure-package example
includes copyable read-only CI and a local quickstart using a real released
renderer and reviewed lock. Guidance prefers named tasks invoking shared
executables; local Roc scripts supply product-specific behavior. CI checks the
starter workflow syntax alongside the existing executable adoption tests.

== Scope and enduring risk explanations

The manual defines its scope as shared tooling, workflow boundaries and
evidence. Contextual narratives connect concrete risks to guiding principles,
specific controls, verification and residual assumptions. A linked reference
indexes those explanations without duplicating their rules. Contribution and
agent instructions keep this pattern part of future changes; scoped research
produces issues and proposals before new practices enter the model.

== Compatibility evidence admission

The runner records normal exits, signals and launch errors separately. Missing
executables cannot satisfy expected exit codes, and interrupted processes cannot
produce a compatibility pass. Application-header admission requires an actual
declared release dependency, ignores comments, rejects compiler constraints and
fails closed for unsupported syntax. Native regression fixtures exercise these
failures through aggregation as well as preserving valid nonzero exit cases.
The dashboard requires a canonical single-job caller, GitHub-resolved shared
workflow identity and a complete job inventory bound to the same run attempt.
Local jobs or shell text cannot impersonate the shared compatibility verdict.

== Verified Blueprint executable cache

`actions/setup-blueprint` caches its executable by default using the exact
release, system and reviewed SHA-256. It restores before installation, verifies
every hit and avoids release requests when those bytes are usable. Corrupt
regular bytes are refetched and checked; symlink/nonregular entries fail closed.
The new `binary-cache-hit` output describes verified reuse; `cache-binary: false`
opts out. Existing `cache` and `cache-hit` still refer only to the separate
Blueprint artifact store. Pins and reviewed digests remain maintainer changes.

== Shared published-release compatibility runner

`actions/release-compatibility` and the `release-compatibility` utility define a
single versioned contract for published examples. The runner resolves one final
product release and one nightly, verifies the selected examples ZIP by its asset
identity and SHA-256, validates its paths and test specification, and checks,
builds and runs the archived applications without changing their dependencies.
Successful compiler stdout and stderr remain visible and are preserved as raw
diagnostic artifacts. Warnings are nonfatal; test failures, infrastructure
failures, skipped cases, timeouts and incomplete target evidence stay distinct.
Only a complete, matching pass on every target can close a compatibility issue.

Compiler pins are changed manually during downstream development. This runner
does not update pins, open upgrade pull requests or merge downstream changes.

== Downstream status in the README

The README lists the scheduled shared published-release compatibility verdict,
its follow-up action, and the exact
roc-automation revisions those repositories reference. The Documentation workflow
refreshes a read-only inventory daily and publishes dated badge endpoints and a
full source-linked report with the manual. It adds no repository write permission
and makes no downstream changes. A version is latest only when every direct
reference equals the observed upstream `main` commit; mixed revisions, unpinned
references and unreadable evidence remain visible. An updater's green outcome
does not count as compatibility evidence. Each publication marks passes over
48 hours old stale. Static badges retain their last colour if publication stops;
an old snapshot date requires investigation. Adoption, infrastructure and upgrade actions remain explicit. Neither
column is a security-compliance claim.

== Release software bills of materials

The release guidance defines a machine-processable SPDX or CycloneDX SBOM for
each deliverable, bound to its exact SHA-256 and target. It distinguishes
shipped components from build/test tooling and source dependencies, includes
transitive, vendored and proprietary components, and requires explicit identity,
license, source and relationship information with declared coverage gaps.

Repositories generate and validate sidecars in read-only release builds and PR
dry runs, distribute them with signature evidence, retain them downstream and
use them for advisory impact analysis. The manual separates component records
from lockfiles, dependency submissions, checksums and provenance, and describes
immutable corrections. Generation and validation belong to the read-only build;
publication verifies and transfers the resulting files as inert bytes.

== Fast PR checks and separate campaigns

Benchmark and fuzz targets expose explicit smoke modes with at most one second
of workload execution per target, excluding compilation and provisioning.
Routine PR checks and release dry runs build and exercise those modes;
benchmark smoke timings establish no performance baseline. Sustained fuzzing
and measured benchmarks use separate schedule/manual jobs with explicit event
guards, so moving work to another job cannot accidentally run it on every PR.

The guidance includes a daily ten-minute total campaign over roc-fuzz's Roc
builtin targets against the latest nightly, with compiler/source identities,
bounded inputs and preserved reproducer artifacts. Campaign results remain
separate from published-release compatibility; failures stay failures and
interrupted or skipped work never establishes compatibility.

== `actions/setup-blueprint` needs no inputs

The action reads the roc-blueprint release from the platform URL in the
checked-out `Blueprint.roc`, and records the reviewed SHA-256 of each release's
binaries itself. See
xref:actions.adoc#setup-blueprint[`actions/setup-blueprint`].

If you followed version 2:

* move the reference to a revision of the action that records your Blueprint
  release;
* delete the `version` and `sha256-*` lines from every call; and
* make sure the checkout step comes before the action.

[source,yaml]
----
- uses: actions/checkout@REVIEWED_FULL_SHA
  with:
    persist-credentials: false
- uses: lukewilliamboswell/roc-automation/actions/setup-blueprint@REVIEWED_FULL_SHA
----

The inputs still work, so an existing call keeps running unchanged. Keep
`version` only in a job that has no checkout, and a `sha256-*` input only to
install a release the action does not record.
xref:maintenance.adoc#upgrade-blueprint[Upgrade Blueprint] is now a change to
`Blueprint.roc` alone.

== `actions/publish-release`

The publish job of `release.yml` calls
xref:actions.adoc#publish-release[`actions/publish-release`] in place of
hand-written steps. It stages a draft at the tested commit, uploads the assets,
downloads each one back and compares it with the tested file, and only then
publishes. It refuses a version that already has a tag, a release or a draft,
and it never asks GitHub to generate notes.

xref:workflows.adoc#recover-an-interrupted-publication[Recover an interrupted publication]
is rewritten to match: a draft left by a failed run is deleted, and the publish
job of the same run is run again.

== `actions/nightly-report`

The report job of `nightly.yml` calls
xref:actions.adoc#nightly-report[`actions/nightly-report`] in place of inline
steps. It keeps the one tracking issue, which is the open issue with the exact
title whose author is a bot account, and it treats any outcome other than
`success` or `failure` as a setup failure that leaves the issue alone.

The shared runner passes only its constrained aggregate outcome after verifying
matching evidence from every declared target. A failed job alone is not proof
of incompatibility; xref:workflows.adoc#reporting[Reporting] explains the
difference.

== Repository settings are checked by a task

`blueprint run check-settings \-- <owner>/<name>`, run from a checkout of
roc-automation, reads a repository's settings from GitHub and reports each line
of xref:settings.adoc#repository-settings[Repository settings] as passing or
failing, with the fix for each failure. It only reads, and it runs on a
maintainer's machine. xref:settings.adoc#confirm-the-settings[Confirm the settings]
describes it.

The chapter is more exact in three places so that the task can check them:

* neither an app nor a deploy key is on a ruleset's bypass list;
* the `release` and `github-pages` environments name the default branch, and do
  not use "Protected branches only"; and
* the tag ruleset targets all tags and restricts both updates and deletions.

This repository now has a `Blueprint.roc` and Roc scripts of its own, checked
by `blueprint run check`.

== A pure Roc package tests on one runner

xref:overview.adoc#a-pure-roc-package[A pure Roc package] names the profile
most repositories follow: no host code, no native inputs, nothing that differs
by target. Such a package runs each workflow on `ubuntu-latest` only, has no
matrix and no aggregate job, and skips the platform chapters.

== Three release rules are settled

* A dry run renders the release notes for the highest version under
  `docs/releases/`.
* The compiler versions follow the rendered notes under the heading
  "Compilers".
* Several bundles in one release each carry a filename prefix that names the
  package, because Roc identifies a package by its URL without the version and
  hash. The prefix is part of the package's identity.

See xref:workflows.adoc#write-the-release-notes[Write the release notes] and
xref:workflows.adoc#several-bundles-in-one-release[Several bundles in one release].

== Precompiled source-policy utility

The tools release adds `roc-policy` for spelling, public documentation, phrasing,
import boundaries, compiler/dependency headers and test accounting. It reads a
selected definition in `Blueprint.roc`, including local constant references and
field access, without evaluating the application. Source checking and test
discovery require no compiler. The optional test runner requires a supplied Roc
compiler and checks verbose PASS locations with normal caching enabled.
See xref:policy.adoc#check-repository-source-policy[Check repository source policy].

Schema 2 adds named rules, embedded or SHA-256-pinned offline policy profiles,
ordered repository/file overrides, explicit collection changes, exclusions,
warning levels and effective-configuration explanations. Repository choices
remain in `Blueprint.roc`; no extra evaluator or runtime network is required.
Schema 1 remains supported.

== Precompiled documentation renderer

`roc-docs` renders HTML and PDF with embedded fonts and Roc highlighting, before
any Roc compiler is installed downstream. The shared documentation action now
uses a supplied renderer binary. AsciiDoc parsing, PNG preparation,
HTML and PDF rendering all run inside that binary, using roc-parser 3.0.0.
The action needs no Python; the renderer also accepts Markdown.
The tools pipeline builds and tests three native targets, alongside `roc-policy`.

The initial native theme replaces our manual's Docker build. Prepared Mermaid
images retain source and image digests; changed diagrams require regeneration.
The Docker backend, custom Asciidoctor themes and the `backend` and
`theme-directory` inputs have been removed. Consumers pinned to earlier SHAs
retain their existing behavior. Rendering rejects unsupported input and stages
output before replacing a prior publication. It does not implement every Asciidoctor extension or PDF theme option.

HTML retains a hierarchical desktop contents sidebar and an expandable mobile
contents list, section numbering, heading links, description lists, boxed
sidebars, figure captions and table proportions. YAML snippets use the parser's
source-preserving tokenizer; shell, JSON and diff examples also retain syntax
colouring. Prepared SVG companions keep website diagrams sharp when zoomed,
with PNG fallback and the existing PNG path for PDF. The HTML theme retains
bundled reading fonts and supports light and dark colour schemes.

== Nix-free utility adoption

The shared Blueprint setup admits `0.7.0` as well as previously reviewed releases,
installs Nix only when requested,
and can cache verified download artifacts by locked logical tool set. A complete
pure-package example keeps the package nightly floating and declares fixed
tooling and released utilities through `Programs`/`Fetch`. The shared
`blueprint-tool` handoff resolves persistent paths and optionally reports
provisioning time, command time/RSS and output sizes. Cold/warm CI fixtures
exercise different tool subsets on fresh runners.

== Native Windows compatibility runners

The shared published-release compatibility runner supports native x64 tests on
`windows-2022` and `windows-2025` alongside Linux and macOS. It preserves native
paths and executable suffixes, validates archives with the same standard-library
helper on every OS, rejects Windows path aliases and case-insensitive environment
overrides, and bounds complete child process trees. CI runs real compiler
check/build/execute smoke tests and unhappy-path regressions on both Windows
images. Windows native prerequisites use `setup-command`. Blueprint 0.7.0 has a
Windows binary; the shared setup action does not map Windows runners yet. Nix
is not a Windows prerequisite backend, so these shared installer options remain
disabled there.

== Static Markdown documentation

The shared documentation utility publishes static chapter Markdown and a
versioned `llms.txt` index alongside HTML and PDF by default.
`--markdown false` or `markdown: "false"` opts out. HTML pages expose visible
Markdown links and standard discovery relations; chapter references and anchors
remain usable under project-site paths. The manual uses this default, with
independent content and link verification before publication. Literal AsciiDoc
inline code preserves attribute placeholders across all published formats.
