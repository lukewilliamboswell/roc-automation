= Proposed design: shared Roc policy utilities
:toc:

Design produced by an Astra agent at High reasoning effort, following review of
the spike and current roc-blueprint interfaces. This is a proposal, not an
implemented interface or a change to the normative automation manual.

== Decision

Build one focused `roc-policy` executable, backed by shared pure Roc libraries
and immutable upstream policy profiles. Each repository declares its facts once
in a named literal binding inside `Blueprint.roc`. Blueprint owns environments
and task execution; the policy utility owns checking those facts against source
and, after evaluation is available, against Blueprint's actual configuration.

Keep release publishing and privileged controllers separate. Other utilities
may run from source through an action with an explicit toolchain contract.
Precompilation is particularly valuable for bootstrap independence and avoiding
utility recompilation under every downstream compiler version.

== Authorities and responsibilities

[cols="1,3",options="header"]
|===
|Authority |Responsibility
|roc-automation utility release
|Rule meaning, profile definitions, schema support and tested implementation dependencies.
|Downstream `Blueprint.roc`
|Repository identity, source roles, package entrypoint, tooling compiler, selected tools release and explicit exceptions.
|Downstream `Blueprint.lock`
|Generated resolutions: artifact URLs, lengths and content hashes. Not another manually authored policy document.
|===

Profiles turn repository facts into obligations. Consumers should not copy the
expanded rule list to configure every repository. Central authority here means
central definitions; repository owners can still change their chosen profile or
workflow through review. This does not itself enforce protection against them.

== Authoring example

This illustrates the proposed schema using existing Blueprint authoring APIs.
The policy schema, executable name and profiles are not released interfaces.
Replace placeholders with the selected immutable release URLs and versions.

[source,roc]
----
app [config] {
    pf: platform "<selected Blueprint platform bundle URL>",
}

import pf.Recipes

repository_policy = {
    schema_version: 1,
    profile: "roc-package/1",
    tools_release: "tools-<version>",
    tooling_compiler: "nightly-2026-10-09-258ab27",
    package: {
        dependency_name: "ansi",
        entry: "package/main.roc",
    },
    source_sets: [
        { path: "package", role: Package },
        { path: "examples", role: Examples },
        { path: "fuzz", role: Fuzz },
        { path: "tests", role: Tests },
        { path: "scripts", role: Tooling },
    ],
    exceptions: [],
}

config = [
    Name("roc-ansi"),
    Systems(["x86_64-linux", "aarch64-linux", "aarch64-darwin"]),
    Environment("policy", [
        Programs([
            Fetch(
                "roc-policy",
                Recipes.file(
                    "https://github.com/lukewilliamboswell/roc-automation/releases/download/${repository_policy.tools_release}/roc-policy-{system}",
                ),
            ),
        ]),
    ]),
    Environment("dev", [
        Extend("policy"),
        Programs([
            Fetch(
                "roc-stable",
                Recipes.roc_nightly(repository_policy.tooling_compiler),
            ),
        ]),
    ]),
    Task("policy", [Use("policy"), Run(["roc-policy", "check", "--root", "."])]),
]
----

Compiler and tools versions each have one authored value. Blueprint references
those fields through ordinary Roc expressions. Discovery follows source sets,
avoiding a separate manually maintained roots list.

The authoritative binding supports literal records, lists, strings, integers
and approved tags. Reject calls, imported values, references, interpolation,
record updates, duplicate fields and unknown fields inside that binding.
Outside it, Blueprint remains ordinary composable Roc. The ordinary compiler
types its uses; an optional upstream schema module can provide a complete
explicit record annotation without copying types into every repository.

This boundary is deliberate: an arbitrary computed policy cannot also be read
before a compiler exists without an interpreter. A later evaluated export can
feed the same internal schema, but must not silently change bootstrap semantics.

== Profile behavior

The initial `roc-package/1` profile should encode the existing floating-package,
pinned-tooling convention. Other repository/compiler conventions need their own
explicit profiles; this is not a universal rule for every Roc project.

* Tooling app headers declare the tooling compiler.
* Package and designated consumer sources do not introduce compiler pins.
* Applicable examples and fuzz/test entrypoints depend on the working-tree
  package. Resolve relative literal dependencies against the source file and
  compare with the canonical package entry, rather than configuring separate
  `../` and `../../` spellings.
* Define applicability explicitly for apps, package headers, known entrypoints
  and headerless modules. Empty required selections and contradictory source
  roles are configuration errors.

Script header pins remain repeated assertions required by Roc's source format;
Blueprint is their authority. Removing the repetitions themselves would require
a separate language or execution change.

Follow-on policies should come from repeated needs: public declaration
documentation, explicit exposures, dependency conventions, import boundaries
and identifier terminology. Syntax-based rules must state their analysis limits.
An import spelling check is not complete binding/call analysis. Documentation
presence is not documentation quality. Compiler diagnostics, formatting,
behavioral tests, fuzz replay and release artifact testing remain existing tasks.

== Versioning and exceptions

Keep configuration schema, profile revision, parser identity and binary release
distinct. A profile revision names a documented set of obligations. New
mandatory obligations require a new profile revision. Implementation fixes may
change findings within the existing contract and must be explained in release
notes.

Exceptions belong beside repository facts and name a stable rule, a narrow
scope and a reason. Report applied exceptions; reject unknown rules,
nonexistent targets and stale exceptions. Avoid an unrestricted profile override
that silently disables every obligation.

== CLI and runtime contract

[source,sh]
----
roc-policy check --root .
roc-policy check --root . --format json
roc-policy explain --root .
blueprint run policy
roc-policy check-blueprint --root . --spec /temporary/blueprint.spec
----

`explain` shows facts, selected profile, expanded rules, applicable paths,
exceptions and parser identity. This keeps central decisions reviewable.

The checker reads files and prints results. It starts no subprocesses, fetches
nothing and changes nothing. Use deterministic discovery and explicit path
semantics, deduplicate overlaps and reject unsupported symbolic-link/special-file
inputs. Do not implicitly depend on Git, locale or ignore files.

Diagnostics need stable rule IDs, paths, UTF-8 byte spans, human locations,
severity and explicit analysis completeness. Version JSON output separately.
Use exit 0 for completed passing checks, 1 for policy violations and 2 for
configuration, unsupported analysis, I/O or invocation failures. This improves
on the spike, which currently reports incomplete parsing as a finding.

== Bootstrap and evaluated agreement

Current Blueprint evaluates `Blueprint.roc` using Roc before resolving the
task's fetched programs. `blueprint run policy` therefore is not itself a
compiler-free bootstrap path.

The proposed complete sequence is:

. Check out candidate sources in an unprivileged job.
. A setup action pinned to a full SHA installs the policy binary without
  evaluating Blueprint. The proposed authority is the exact program entry for
  the runner in `Blueprint.lock`: validate its supported structure and expected
  release location, then check the downloaded length and SHA-256 before use.
. Run source policy by extracting the literal binding and expanding the profile.
. Start Blueprint normally, with its own evaluation compiler requirements.
. Produce a transient evaluated Spec with `blueprint spec`, checking that the
  command succeeded. Supply it to `check-blueprint` to compare actual program
  declarations with canonical policy facts for the declared systems.
. Continue existing compiler, format, test, build and release checks.

The setup action and its narrow lock-reader contract are new work and the
largest addition beyond the checker. It must not become a second general
Blueprint resolver. Share the lock model/validation where practical and test
schema compatibility. State its host download/runtime requirements explicitly.

The agreement step is necessary: a literal declares intended facts but cannot
prove arbitrary later expressions actually use them. The evaluated Spec is
temporary evidence, not a second committed configuration. It lets the utility
check compiler and policy-program declarations without interpreting Roc.

Current Blueprint also has `Custom` settings lowered into Spec extensions. A
typed upstream adapter can use that later for policy export. This adds no
bootstrap magic, is not required initially, and should not make Blueprint core
responsible for ecosystem policy profiles.

== Grammar compatibility

Find exactly one top-level policy binding structurally, allowing normal
headers, imports, annotations and unrelated declarations. Comments, strings and
nested lookalikes must not count. Initially require the whole Blueprint to parse
completely rather than guessing declaration boundaries in a recovered tree.

That creates a real compatibility responsibility. The utility's build compiler,
the parser library and inspected source grammar are distinct. Publish their
identities and test representative Blueprint/source versions, including older
compiler generations. Preserve minimized incompatibilities as fixtures.

The spike pins parser 2.1.0-rc.1 and builds with
`nightly-2026-10-15-38e6c42`; the parser's syntax reference is independently
pinned. Complete parsing does not establish type correctness or universal
agreement with every compiler. Unsupported/recovered/limited input must produce
an actionable incomplete-analysis result without a text-scanning fallback.
Performance optimization is outside this design's immediate acceptance criteria.

== Distribution and utility boundaries

Use existing `tools-<version>` releases. Build with pinned implementation
dependencies and test the exact artifacts upstream without a compiler. Begin
with x86_64 Linux, ARM64 Linux and Apple Silicon macOS, using distinct tested
platform contracts. Do not imply support for Intel macOS or Windows. Blueprint
recipes must return `Unavailable` or limit declared systems when assets do not
exist.

Consumer adoption reviews release and lock changes. Routine execution verifies
admitted bytes. Content hashes establish byte identity, not build provenance.
Never evaluate candidate Blueprint configuration in privileged controller jobs.

Group related source-analysis operations in one executable: they share parsing,
configuration, discovery and diagnostics. Keep privileged release/report
utilities separate. Share pure libraries and tests upstream rather than creating
a binary per lint rule or one executable for all automation capabilities.

Source-run utilities remain valid where appropriate. Their action contract must
name a provided compiler requirement and locked source/platform dependencies;
they should not accidentally borrow whatever compiler a consumer is testing.

== Migration and acceptance

. Replace the spike's separate config with literal Blueprint extraction and one
  package profile. Test valid ordinary Blueprint syntax and hostile lookalikes.
. Migrate roc-ansi compiler-pin and working-tree dependency checks, deleting
  equivalent scanners while retaining behavior coverage and compiler/tests/build
  workflows. Handle relative paths through canonical package identity.
. Add stable diagnostics, `explain`, JSON output, exceptions and evaluated-Spec
  agreement tests.
. Integrate exact-artifact release tests and the compiler-free installer contract.
. Adopt Blueprint import policy as a second consumer, preserving bespoke provider
  architecture checks that the generic import rule cannot establish.

Prove a real removal of downstream scanner code and runtime requirements,
equivalence for migrated policies, rejection of deliberately changed dependencies,
one authored value for compiler/tool versions, and successful checks before Roc
is available. Preserve regression coverage for Unicode locations, incomplete
parses, irrelevant config fields, exceptions and bootstrap lock mismatches.

Defer source rewriting to an explicit editing operation or separate utility.
Lossless syntax makes it promising, but file mutation changes the checker's
simple read-only contract.
