= roc-docs

`roc-docs` renders Markdown to a website page and a searchable, tagged PDF 2.0.
The released executable embeds its licensed fonts and Roc lexical highlighter.
Rendering needs no Roc compiler, Docker, Ruby, Node, browser, Python, host fonts
or network. The shared action uses Python's standard library to prepare the
supported AsciiDoc subset and assemble a multi-page site; that preparation is
separate from the native renderer.

[source,sh]
----
roc-docs render manual.md new-output \
  --title 'Project manual' --author 'Project contributors' \
  --version 1.2 --language en-AU --pdf-filename project.pdf
----

The output directory must not exist. Both requested formats are prepared before
any publication. Files are written to a new sibling staging directory, then
renamed into place; existing output is never replaced by this CLI. The action
adds its own workspace checks and final directory publication. `--html-only`
and `--pdf-only` support assembling a multi-page site and a combined manual.
An interrupted write can leave `<output>.roc-docs-stage`; review and remove that
directory before retrying. The renderer refuses to reuse it.

== Authoring and assets

The native input is Markdown parsed by roc-parser. Supported blocks are
headings, paragraphs, fenced code, ordinary lists, tables, quotes and thematic
breaks. PDF quote content is retained as body paragraphs; the initial PDF theme
does not reproduce the HTML quote indentation. Roc fences use original UTF-8 lexical ranges in HTML and PDF; other
languages retain preformatted text. Raw HTML, unsupported inline constructs and
unknown images fail explicitly. Links permit HTTP(S), mailto, local fragments
and, in HTML, safe relative paths; executable URL schemes are rejected. PDF
links require absolute URLs or internal destinations; the action rewrites
manual cross-references to internal destinations. The renderer
does not fetch remote content.

Headings may use an explicit trailing `{#stable-id}`. Duplicate explicit IDs
fail. Repeated implicit labels acquire `-2`, `-3` and subsequent suffixes.
Unicode labels retain their UTF-8 characters in implicit IDs. Cross-page links
are ordinary relative links; the action preparation stage indexes the complete
manual and rewrites links for HTML pages and the combined PDF separately.

Images are runtime assets, not compiled repository-specific fixtures:

[source,sh]
----
roc-docs render manual.md new-output \
  --asset images/example.png example.png example.rgb 640 480
----

The paired inputs are the original PNG copied into HTML and tightly packed RGB8
bytes used by PDF. Width and height describe their pixel dimensions. The action
preparer validates and decodes supported non-interlaced 8-bit RGB/RGBA PNGs,
including chunk checksums, and composites alpha onto white. This is a prepared
asset interface, not a general native PNG decoder. The CLI independently checks
RGB lengths, PNG signatures, dimensions and resource limits. It fits figures to
the A4 body and retains alt text. `--pdf-image-dpi` sets a maximum PDF raster
resolution from 72 to 300 DPI, default 144. Deterministic box averaging reduces
oversized RGB rasters; it never upscales small originals. HTML retains each
original PNG byte-for-byte. The initial roc-pdf facade has a fixed resource
budget, so a large manual at a higher resolution may fail explicitly before
publication; reduce PDF resolution or image dimensions rather than dropping
figures.

The initial theme is built in. Existing Asciidoctor YAML themes are incompatible;
the action rejects them with the Roc backend. Custom themes and broader image
formats require an explicit future interface. A PDF outline and linked contents
are provided; printed contents page numbers and chapter-aware running headers
are not currently implemented. Font shaping support is limited by roc-pdf and
the embedded faces; unsupported requests must fail rather than substitute text.

== Build and verify

Use compiler `nightly-2026-10-15-38e6c42` and its normal cache. Package URLs in
`main.roc` pin basic-cli, roc-parser and roc-pdf by content hash. The build script
uses the validated `--opt=speed` configuration; compilation has substantial RAM
cost even though rendering is small and fast.

[source,sh]
----
ROC=/absolute/path/to/roc roc tools/roc-docs/build.roc aarch64-darwin
ROC_DOCS_BINARY="$PWD/dist/roc-docs-aarch64-darwin" \
  python3 tools/roc-docs/tests/test_cli.py
roc test tools/roc-docs/test_highlight.roc
roc test tools/roc-docs/test_assets.roc
python3 -m unittest discover -s tools/roc-docs/tests -p test_prepare_docs.py -v
----

The binary harness runs renderer subprocesses with `PATH=/nonexistent`.
Independent PDF-reader tests additionally use optional Poppler tools installed
on the verification host; those are not render-time dependencies. They check
actual token colours, tagged output, continuing source/table content, source
bytes in HTML, runtime assets, metadata, determinism and rejection before
publication. The action tests additionally exercise multi-page assembly and
workspace/publication boundaries. Passing these checks is not an independent
PDF/A or PDF/UA compliance claim.

`SyntaxHighlight.roc` is a pure reusable module with no PDF, HTML, font or
platform dependency. `Renderer.roc` holds the reusable Markdown adaptation,
HTML/PDF theme and registered fonts; `main.roc` owns CLI parsing, runtime asset
reads and publication. Renderer code was adapted from roc-ansi commit
`75df8efb085fb5f5fd90f5909a49dd7f5e364dcc`, copyright 2023 Luke Boswell and
subsequent authors, under UPL 1.0. Font files retain their SIL OFL notices and
pinned hashes in `fonts/provenance.json`. `roc-docs --licenses` prints bundled
font notices without requiring adjacent files.

== Prepare a repository manual

The standard-library adapter preserves top-level page routes and prepares the
entrypoint include tree as a combined PDF input:

[source,sh]
----
python3 tools/roc-docs/prepare_docs.py --workspace . \
  --docs-directory docs --entrypoint index.adoc \
  --output-directory .docs-prepared --docs-version 1.2 \
  --pdf-filename project-1.2.pdf
----

`.docs-prepared/manifest.json` identifies metadata, each page's Markdown input
and HTML output, the combined manual input/output, prepared image paths and
source/heading/code/table inventories. Paths are relative to that new preparation
directory. The shared action consumes this manifest; rendering alone never
executes a converter. See link:PREPARATION.adoc[the preparation contract] for
schema details and precise supported AsciiDoc constructs and adaptations.
Unknown structural directives, references and attribute references fail.
Ordinary text that happens to resemble an unsupported inline extension is not a
general AsciiDoc validator: inspect the prepared/rendered content when adopting
a new authoring convention.

Native Markdown makes each top-level `.md` file a website page, but the PDF uses
only the selected entrypoint. Markdown includes and automatic cross-file PDF
link rewriting are not implemented. Use absolute URLs or destinations present
in that PDF entrypoint. The AsciiDoc adapter indexes its include tree and rewrites
its supported cross-references for the combined PDF.

Mermaid diagrams are prepared authoring assets. To register downstream diagrams,
add `docs/prepared-diagrams.json`:

[source,json]
----
{
  "schema_version": 1,
  "diagrams": [{
    "source_sha256": "<SHA-256 of the exact Mermaid body>",
    "href": "images/build-flow.png",
    "png": "images/build-flow.png",
    "png_sha256": "<SHA-256 of the prepared PNG bytes>"
  }]
}
----

The source hash covers body lines joined by LF, including the final LF, excluding
AsciiDoc block markers. `png` is relative to the documentation directory; `href`
is the safe published image path. An edited diagram fails until its prepared
PNG and source hash are updated. Local registrations override the bundled
repository corpus. Preparation verifies PNG hashes/chunk CRCs and supports
non-interlaced eight-bit RGB/RGBA, compositing alpha onto white for PDF. Runtime
builds use the recorded PNG and need no Mermaid/browser tooling.
