= Native documentation preparation

`roc-docs build` and `roc-docs prepare` run entirely in the released Roc binary.
`Preparation.roc` is a pure adapter over roc-parser 2.1.0-rc.3's public AsciiDoc
syntax tree, virtual-file preprocessing and inline rendering APIs. Files and
source-linked diagram registrations are supplied as inert data by
`RepositoryBuild.roc`. No author input is executed and includes cannot fetch
network content.

[source,sh]
----
roc-docs build --workspace . --docs-directory docs --entrypoint index.adoc \
  --output-directory .docs-out --docs-version 3 --pdf-filename manual.pdf
roc-docs prepare --workspace . --docs-directory docs --entrypoint index.adoc \
  --output-directory .docs-prepared --docs-version 3 --pdf-filename manual.pdf
----

`build` renders AsciiDoc HTML directly from the syntax tree to preserve block
semantics, while the combined PDF uses prepared Markdown. Native Markdown shares
the same HTML page layout and source highlighters.
`prepare` writes intermediate Markdown/assets and a schema-2 debugging inventory
into a new directory. It is useful for reviewing parser adaptation independently
of PDF layout. Its metadata, page inputs/routes, manual input/output, image
identities/dimensions and source hashes are experimental inspection data.
The shared action calls native `build` directly and does not consume a Python
preparation manifest.

== Source boundaries

Source and output paths remain within the explicit workspace. Symlinks and
special files reject; output overlap with the source tree rejects. Source size,
file count, include depth, prepared output, images and decompression are bounded.
A build stages every page, image and PDF before publishing. Failure preserves
previous output; stale publication stages/backups are never silently reused.

Native Markdown uses roc-parser's Markdown AST for image discovery and rendering.
Top-level Markdown files become site pages; the chosen entrypoint alone supplies
the PDF. Markdown include directives and automatic cross-file PDF link rewriting
are not implemented. Relative website links require a deliberate absolute URL
or internal destination in the PDF input.

The AsciiDoc adapter supports virtual local includes with level offsets,
backend HTML/PDF conditionals, attributes, document/section headings and explicit
IDs, ordinary lists, description/sidebar content, LF source blocks, header PSV
tables with continued cells, captions, links/cross-references, local PNG images
and source-linked Mermaid assets. Top-level AsciiDoc pages retain their `.html`
routes. The entrypoint include tree supplies the combined PDF; its cross-references
resolve against indexed source paths/headings rather than accidental page order.

The adapter rejects unsupported block contexts, raw HTML/passthrough, custom
source substitution/indent modes, unsafe paths, unknown diagram bodies,
unresolved references and unsupported table modes. The rendering subset does not
claim general Asciidoctor compatibility. Source body bytes are recovered from
original files when the upstream AST normalizes trailing whitespace; ambiguous
original bodies reject rather than guessing. The acceptance corpus checks every
manual source block against the original source inventory.

== Explicit presentation adaptations

HTML preserves description lists as `dl`/`dt`/`dd`, boxed sidebars and
admonitions, numbered figure captions and authored table column weights. It uses
a nested persistent contents sidebar on desktop and an expandable single-column
contents list on mobile. AsciiDoc section numbering and contents depth are
preserved, including legacy duplicate-heading aliases.

PDF presentation remains different from Asciidoctor: description lists use bold
labels and sidebar/caption content remains ordinary document content. Header PSV
table content is preserved, but PDF column weights and advanced table spans/styles
are not implemented.

HTML retains nested list structure, including attached code blocks. Roc-pdf's
current list item model accepts only paragraphs and nested lists. PDF lists that
contain source blocks, figures or tables therefore retain visible item markers
and all content as body flow blocks. Such complex PDF lists lack the original
list-container semantics; source still uses searchable native code blocks and
retains syntax colours. Ordinary PDF lists retain native list semantics.

Printed contents page numbers, chapter-aware running headers and Asciidoctor
YAML theme compatibility are not implemented. Font/shape limits come from the
pinned PDF engine and embedded faces; unsupported requests fail explicitly.

== Images and diagrams

The executable embeds seven source-linked prepared diagrams with source-body,
PNG and SVG SHA-256 identities. HTML prefers validated SVG companions with PNG
fallback; PDF continues to decode PNG. Local `prepared-diagrams.json` registrations can
override them. See link:README.adoc[the utility README] for the registry schema
and exact LF/final-newline source-hash convention. A changed Mermaid body or
image hash fails until its prepared asset is deliberately updated. Creating a
new Mermaid image remains an authoring-time choice, outside the build runtime.

`Png.decode` validates chunk CRCs, zlib header/Adler32 and exact pixel lengths,
with output/work bounds enforced during decompression. It supports non-interlaced
eight-bit RGB/RGBA only. Alpha is composited onto white for PDF; HTML retains the
original PNG. PDF-only box averaging uses the requested 72–300 DPI cap, default
144, and never upscales originals. Large manuals at higher resolutions can
exceed the PDF engine's resource budget and fail before publication.

== Independent verification

The previous Python adapter lives only under `tests/` as an independent source
inventory/reference implementation. Python and optional Poppler tools are test
host dependencies, not production build dependencies. The real native CLI is
tested with external tooling unavailable on `PATH`. Reference inventories compare
all emitted HTML code bytes, table/image counts, anchors and cross-page links;
independent PDF reader checks cover code characters, destinations and actual
highlight colours. These tests do not establish PDF/A or PDF/UA compliance.
